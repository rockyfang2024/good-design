## 5.1 TCP 拥塞控制：防止网络过载

### 问题

网络中有 1000 个连接同时传输数据，如果它们都全力发送，路由器队列溢出 → 大量丢包 → 重传 → 进一步加剧拥塞 → 恶性循环。怎么控制？

### 经典解法：TCP 拥塞控制四件套

**1. 慢启动（Slow Start）**

```python
# 连接开始时，不知道网络容量多大
# 用"探索"的方式逐步增加发送速率

cwnd = 1  # congestion window，单位：MSS（最大段大小）

def send_data():
    # 每收到一个 ACK，cwnd += 1
    # 指数增长：1 → 2 → 4 → 8 → ...
    while cwnd < ssthresh:
        cwnd *= 2
```

**2. 拥塞避免（Congestion Avoidance）**

当 cwnd 超过阈值（ssthresh），切换到线性增长：

```python
def on_ack():
    if cwnd >= ssthresh:
        cwnd += 1  # 线性增长，每个 RTT 加 1 MSS
    else:
        cwnd *= 2  # 指数增长（慢启动）
```

**3. 快速重传（Fast Retransmit）**

收到 3 个重复 ACK，说明数据包丢了，但不一定是网络拥塞：

```python
# 不等超时，快速重传丢失的包
dup_ack_count = 0

def on_duplicate_ack(expected_seq):
    dup_ack_count += 1
    if dup_ack_count == 3:  # 3个重复ACK
        # 快速重传丢失的段
        retransmit_segment(expected_seq)
        ssthresh = cwnd / 2  # 阈值减半
        cwnd = ssthresh      # 窗口减半
```

**4. 快速恢复（Fast Recovery）**

```python
# 快速重传后，进入快速恢复
cwnd = ssthresh + 3  # 稍微加大窗口
# 然后每收到一个重复ACK，cwnd += 1
# 收到新数据的ACK后，退出快速恢复
```

### 拥塞窗口 vs 发送窗口

```python
# 实际发送窗口 = min(拥塞窗口, 接收窗口)
effective_window = min(cwnd, receiver_window)
```

**核心原则**：网络是共享资源，拥塞控制通过"探索 + 退让"让多个连接公平地使用网络带宽。

## 5.2 连接管理：TCP 三次握手与四次挥手

### 问题

为什么 TCP 建立连接需要三次握手，关闭需要四次？

### 三次握手（建立可靠连接）

```
客户端                          服务器
  │                               │
  │ ─── SYN (seq=x) ─────────────▶│  客户端发送 SYN
  │                               │
  │ ◀── SYN+ACK (seq=y, ack=x+1) ──│  服务器同意，并确认
  │                               │
  │ ─── ACK (ack=y+1) ──────────▶ │  客户端确认
  │                               │
  │         连接建立              │
```

**为什么三次**：
- 第一次：客户端证明自己能发
- 第二次：服务器证明自己能收、能发
- 第三次：客户端证明自己能收

**两次不够吗**：如果第二次包（服务器的 SYN+ACK）丢了，服务器以为自己建立了连接，但客户端没收到 → 服务器空等，浪费资源。

### 四次挥手（优雅关闭）

```
客户端                          服务器
  │                               │
  │ ─── FIN ────────────────────▶│  客户端：我没数据了
  │ ◀── ACK ─────────────────────│  服务器：收到
  │                               │  （此时客户端不能再发数据，但服务器可能还有数据要发）
  │ ◀── FIN ─────────────────────│  服务器：我也没了
  │ ─── ACK ────────────────────▶│  客户端：收到
  │                               │
  │    TIME_WAIT (2MSL)           │  等待残余数据包消失
  │                               │
```

**为什么四次**：服务器收到 FIN 时，可能还有数据要发，所以先回 ACK，等数据发完了再发自己的 FIN。

**TIME_WAIT 的作用**：
- 确保最后一个 ACK 能到达（如果丢了，服务器会重发 FIN）
- 让老的重复数据包在网络中消失，防止影响新连接

## 5.3 HTTP/2 与 HTTP/3：协议进化

### HTTP/1.1 的问题

```
队头阻塞（Head-of-Line Blocking）：
  请求1 ──────────────────▶
  请求2 ─▶（必须等请求1完成）
  请求3 ─▶（必须等请求2完成）
```

即使带宽足够，请求是串行的，速度上不去。

### HTTP/2 的解法：多路复用

```python
# 一个 TCP 连接上，多个流并发传输
# 流 ID 标识每个请求/响应
#
# 帧（Frame）：最小传输单元
#   - HEADERS 帧：请求头
#   - DATA 帧：请求体/响应体
#
#         连接
#    ┌────┬────┬────┐
#    │流1 │流2 │流3 │  ← 三个流并行
#    │数据│数据│数据│
#    └────┴────┴────┘
```

**优点**：一个 TCP 连接，多个请求并行。解决 HTTP/1.1 的队头阻塞。

**新问题**：TCP 层面的队头阻塞还在。如果一个包丢了，所有流都被阻塞。

### HTTP/3 的解法：QUIC

```python
# QUIC = UDP + 可靠性
# 基于 UDP，但实现了：
#   - 多路复用（类似 HTTP/2）
#   - 连接迁移（切换网络时不需要重建连接）
#   - 0-RTT（之前连接过，可以直接发数据）
#   - 内置 TLS 1.3

# HTTP/3 vs HTTP/2
#
# HTTP/2: TCP → TLS → HTTP/2
# HTTP/3: UDP → QUIC → HTTP/3
#
# QUIC 在用户空间实现，不受内核控制 → 迭代更快
```

**核心改进**：
- UDP 没有队头阻塞（每个 QUIC 流独立）
- 丢包只影响丢包那个流，不影响其他流

## 5.4 API 设计原则：接口即契约

### RESTful API 设计

```python
# 好的 API 设计

# 资源命名
GET    /users           # 列出用户
GET    /users/123       # 获取单个用户
POST   /users           # 创建用户
PUT    /users/123       # 完整更新
PATCH  /users/123       # 部分更新
DELETE /users/123       # 删除用户

# 状态码语义明确
200 OK                    # 成功
201 Created               # 资源创建成功
204 No Content            # 成功，但没有返回体（如 DELETE）
400 Bad Request           # 客户端请求错误
401 Unauthorized          # 未认证
403 Forbidden             # 无权限
404 Not Found             # 资源不存在
409 Conflict              # 冲突（如重复创建）
500 Internal Server Error # 服务器错误
```

### 版本管理

```python
# 方式一：URL 路径版本
GET /api/v1/users
GET /api/v2/users

# 方式二：Header 版本
GET /api/users
Accept: application/vnd.api+json; version=v1

# 方式三：Query 参数（不推荐）
GET /api/users?version=1
```

### 幂等性设计

```python
# GET：天然幂等（不会改变服务器状态）
# HEAD：天然幂等
# PUT：幂等（多次 PUT 相同结果）
# DELETE：幂等（多次 DELETE 结果一样）
# POST：非幂等（每次 POST 创建新资源）

# 重试安全：如果 POST 请求超时，应该查状态，不要盲目重试
def create_resource(data):
    response = post('/users', data)
    if timeout:  # 超时，不知道是成功还是失败
        # 查询创建的资源状态
        existing = get('/users', params={'email': data['email']})
        if existing:
            return existing  # 已创建，不重复创建
        raise RetryableError()
```

## 5.5 心跳与健康检查：保持连接活性

### 问题

服务器和客户端建立了长连接，但如果客户端崩溃了（没有发关闭信号），服务器怎么知道连接已经死了？

### 经典解法：心跳机制

```python
# TCP Keepalive（操作系统级别）
# /proc/sys/net/ipv4/tcp_keepalive_time = 7200  # 空闲2小时后开始探测
# /proc/sys/net/ipv4/tcp_keepalive_intvl = 75  # 探测间隔75秒
# /proc/sys/net/ipv4/tcp_keepalive_probes = 9   # 9次无响应则认为死亡

# 应用层心跳（更灵活）
class HeartbeatConnection:
    def __init__(self):
        self.last_ping = time.now()
        self.heartbeat_interval = 30  # 每30秒发一次

    def send_ping(self):
        self.last_ping = time.now()

    def check_alive(self):
        if time.now() - self.last_ping > 3 * self.heartbeat_interval:
            # 连续3次没收到回复
            return False  # 连接已死
        return True
```

### 健康检查设计

```python
# 主动探测：负载均衡器定期 ping 服务器
class LoadBalancer:
    def health_check(self, server):

            return response.status == 200 and response.json()['healthy']

            return False
```

**设计原则**：
- 心跳间隔要小于超时阈值
- 健康检查要有合理的判断逻辑（不是简单的"端口可达"）
- 摘除节点时要有缓冲（防止流量瞬间打到其他节点）
