## 1.1 有限状态机（FSM）：一切控制逻辑的原型

### 问题

你需要设计一个交通灯控制系统。灯有三种状态：红、黄、绿。规则是：

```
绿 → 黄 → 红 → 绿 → ...
永远不能两个灯同时亮
```

你怎么保证系统永远不会进入"两个灯同时亮"的状态？

### 经典解法：有限状态机

```python
class TrafficLightFSM:
    """状态机：状态是有限的，转移是确定的"""

    states = ['GREEN', 'YELLOW', 'RED']
    initial_state = 'GREEN'

    # 状态转移表：当前状态 + 事件 → 下一状态
    transitions = {
        ('GREEN',  'timeout'): 'YELLOW',
        ('YELLOW', 'timeout'): 'RED',
        ('RED',    'timeout'): 'GREEN',
    }

    def __init__(self):
        self.state = self.initial_state

    def handle_event(self, event):
        key = (self.state, event)
        if key in self.transitions:
            self.state = self.transitions[key]
        # else: 忽略无效事件（系统永远不会漂移）
```

**核心约束**：
- 状态数量有限（不是无限可能）
- 每个状态对每个输入有确定的下一步
- 初始状态已知

**为什么重要**：TCP 协议、语法分析器、游戏 AI、协议解析——凡是需要"在有限种状态之间可靠切换"的场景，都基于 FSM。

### 延伸：状态机 vs 条件嵌套

```python
# 坏的设计：深层嵌套的条件
if state == 'LOGGED_IN':
    if has_permission:
        if not is_suspended:
            do_action()
        # else: handle suspended
    # else: handle no permission
# else: handle not logged in
# ↑ 问题：如果加了新状态，这段代码会指数级膨胀

# 好的设计：状态机
def handle(action):
    next_state = transitions.get((self.state, action))
    if next_state:
        self.state = next_state
    # 新状态只需要加 entries 到 transitions 字典
```

## 1.2 递归与分治：化繁为简的利器

### 问题

归并排序为什么比冒泡排序快？凭什么"分而治之"能突破 O(n²) 的限制？

### 核心思想

```
大问题 = 分解成小问题
小问题 = 独立求解
合并结果
```

**关键洞察**：分解后的小问题之间互不依赖，可以并行处理。

```python
def merge_sort(arr):
    if len(arr) <= 1:  # 基例：足够小时不再分解
        return arr

    mid = len(arr) // 2
    left  = merge_sort(arr[:mid])   # 独立子问题
    right = merge_sort(arr[:mid])   # 独立子问题

    return merge(left, right)      # 合并结果
```

**复杂度分析**：

| 步骤 | 操作 |
|------|------|
| 分解 | O(n) — 把数组分成两半 |
| 递归 | 2 × T(n/2) — 两个子问题 |
| 合并 | O(n) — 线性合并 |

递推式：T(n) = 2T(n/2) + O(n)

**Master 定理**：T(n) = O(n log n)

这就是为什么归排是 O(n log n)，而冒泡是 O(n²)。

## 1.3 抽象数据类型（ADT）：接口与实现分离

### 问题

你需要写一个"容器"，存放数据。支持两种操作：放入（push）和取出（pop）。

如果只能选一种数据结构，用什么？

### 经典解法：栈 vs 队列 vs deque

```python
# 栈（Stack）：后进先出
# 场景：函数调用、撤销操作、表达式求值
class Stack:
    def push(self, item): ...
    def pop(self) -> item: ...

# 队列（Queue）：先进先出
# 场景：任务调度、消息队列、 breadth-first search
class Queue:
    def enqueue(self, item): ...
    def dequeue(self) -> item: ...

# 双端队列（Deque）：两端都能 push/pop
# 场景：滑动窗口、最长前缀匹配
class Deque:
    def push_left(self, item): ...
    def push_right(self, item): ...
    def pop_left(self) -> item: ...
    def pop_right(self) -> item: ...
```

**设计要点**：
- **接口不变**：`Stack` 的使用者不需要知道底层是数组还是链表
- **实现可换**：底层可以从数组换成链表，对外接口保持不变
- **复杂度权衡**：数组实现 pop O(1) 但 push 可能 O(n)；链表相反

## 1.4 确定性 vs 非确定性：图灵机的分叉

### 核心问题

P = NP 是什么意思？为什么这个问题这么难？

### 简化理解

**确定性图灵机（DTM）**：每一步，下一步是唯一确定的
```
状态 A + 读到的符号 B → 状态 C + 写的符号 D + 移动方向 E
```
**非确定性图灵机（NTM）**：每一步可以"同时"选择多个可能的转移
```
状态 A + 读到的符号 B → [状态 C/写 D/右移] OR [状态 F/写 G/左移]
```

关键洞察：**NTM 不比 DTM 强大**（可以证明它们等价），但NP问题正是用"能否在多项式时间内验证"来定义的。

```
P = 能在多项式时间找到解
NP = 能在多项式时间验证解（不需要找到，给一个证书/certificate就行）
NP-hard = 至少和 NP 最难的问题一样难
NP-complete = 同时是 NP 和 NP-hard
```

**为什么 P=NP 是 open problem**：因为要证明两者不等，需要证明"不存在任何多项式算法能解决某个特定 NP 问题"——这等于穷尽所有可能的算法，这是无限的搜索空间。

## 1.5 图灵完备性：计算的边界

### 核心概念

**什么情况下一个系统是"图灵完备"的**？

当它能模拟任何图灵机。它就能计算任何（可计算的）函数。

**图灵完备的系统**：
- 大多数编程语言（Python, C, JavaScript...）
- LLVM IR
- 以太坊智能合约（Gas 是资源限制，不是计算限制）
- Excel 公式（某种程度上）

**不是图灵完备的**：
- 正则表达式（标准版）
- HTML/CSS（不是图灵完备）
- PROP 逻辑

**实际意义**：如果你能用一个系统实现另一个图灵完备系统的所有功能，你就知道这个系统"计算能力足够强"。反过来，如果限制图灵完备性（比如 SQL），你就拥有了**可预测的性能**——这是有意为之的设计选择。
