# 6.10 内核调度器的演进：从 O(1) 到 EEVDF

> Linux 调度器经历了四次重大迭代。每次演进都是为了解决上一代的某个根本性缺陷。

---

## 问题

- 进程数增加时，调度延迟不能线性增长
- 交互进程需要快速响应，批处理需要高吞吐
- 不能让任何进程"饿死"

---

## 各代调度器对比

```
O(n) 调度器（Linux 2.4）：
  → 每次调度遍历所有进程，找到最高优先级
  → 进程数增加时，调度延迟线性增长

O(1) 调度器（Linux 2.6.0）：
  → 每个优先级一个运行队列，调度 O(1)
  → 问题：交互进程优先权是静态的，批处理会"偷"走交互时间

CFS（Linux 2.6.23，2007）：
  → 红黑树，按虚拟运行时间排序
  → 完全公平，但响应延迟不理想（"湿地效应"）
  → 问题：I/O 密集型任务可能饿得太久

EEVDF（Linux 6.6，2023）：
  → 取代 CFS，成为默认调度器
  → 思想：每个进程有 "eligible time" 和 "deadline"
  → 优先调度"最早符合条件的进程"
  → 同时照顾延迟（交互）和吞吐（批处理）
```

---

## O(n) → O(1) 的跃迁

**问题**：遍历所有进程找最高优先级，当进程数达到几千时，调度本身成为负担。

**解法**：为每个优先级维护一个独立的运行队列。

```
O(1) 调度器的核心数据结构：
  runqueue[140]  // 每个优先级一个队列（0=最高，139=最低）
  bitset[NR_CPUS]  // 每个 CPU 的就绪队列

调度时：找到最高的非空队列 → O(1)
```

**局限**：优先权是固定的——一个"CPU 密集型批处理进程"只要在队列 1，它就永远比队列 0 的进程优先级低，不管它跑了多久。

---

## CFS（完全公平调度器）

**核心设计**：红黑树，按"虚拟运行时间（vruntime）"排序。

```
CFS 红黑树（按 vruntime 排序）：
    进程B (vruntime=10ms)          ← 调度器选择这个（最"饿"）
         ↓
    进程A (vruntime=30ms)
         ↓
    进程C (vruntime=80ms)
         ↓

vruntime 越小 = 越"饿" = 越应该被调度
```

**调度延迟控制**：

```bash
# sched_latency：每个调度周期要覆盖所有运行中的进程
# 默认 6ms
cat /proc/sys/kernel/sched_latency_ns

# min_granularity：防止进程时间片太小（切换开销）
# 默认 0.75ms
cat /proc/sys/kernel/sched_min_granularity_ns
```

**CFS 的问题——"湿地效应"（thundering herd）**：

当大量 I/O 密集型任务同时从睡眠中醒来时，它们 vruntime 都很少，同时涌入调度器，导致调度器在它们之间频繁切换，而 CPU 密集型任务被饿死。

---

## EEVDF（Earliest Eligible Virtual Deadline First）

**核心思想**：每个任务有两个时间轴——"eligible time"（最早可被调度时间）和 "deadline"（最晚必须完成时间）。

```python
# 每个任务有两个属性
class Task:
    eligible_time   # 最早可以被调度的时间
    deadline        # 最晚必须完成的时间

# 调度决策：选 eligible time 最小的任务
def pick_next():
    # 只考虑 deadline > eligible time 的任务
    candidates = [t for t in runqueue if t.deadline > t.eligible_time]
    return min(candidates, key=lambda t: t.deadline)
```

### 为什么 EEVDF 更好？

| 维度 | CFS | EEVDF |
|------|-----|-------|
| 核心指标 | vruntime（谁跑得最少） | deadline（谁最紧急） |
| 延迟保证 | 无（公平但可能饿死） | 有（deadline 前必调度） |
| 交互响应 | 一般（受湿地效应影响） | 好（I/O 任务的 deadline 短） |
| 吞吐 | 高 | 高（与 CFS 相当） |

### EEVDF 的本质

```
CFS 的问题：公平 ≠ 及时
EEVDF 的解决：公平 + 及时

CFS：让每个进程按 vruntime 排队，调度最"饿"的
EEVDF：给每个进程一个 deadline，在它变得"紧急"之前先调度它

本质上，EEVDF 在 CFS 基础上增加了一个"延迟敏感度"维度
```

---

## 调度器的演进规律

```
问题               →  解法                →  新问题
─────────────────────────────────────────────────────
O(n) 遍历太慢       →  每个优先级一个队列     →  优先权固定，无法动态调整
静态优先权          →  CFS 按 vruntime 公平  →  湿地效应，I/O 任务饿
公平但不及时        →  EEVDF deadline 机制   →  新问题待发现
```

**核心洞察**：没有完美的调度器——每次改进都在"公平性"、"吞吐量"、"延迟"之间做权衡。理解演进历史，能帮助你在遇到新的调度问题时做出更好的设计决策。
