# 6.10 内核调度器的演进：从 O(n) 到 EEVDF

> Linux 调度器经历了四次重大迭代。每次演进都是为了解决上一代的某个根本性缺陷。
>
> **类比**：就像城市交通管理的发展——从"交警站在路口凭感觉指挥"（O(n)）→"每个方向固定配一个交警"（O(1)）→"根据每辆车等了多久轮流放行"（CFS）→"给每辆车设定最晚到达时间，优先让快迟到的先过"（EEVDF）。

---

## 生活场景：十字路口交通调度演进

```
第一代（O(n)）：交警数汽车
  路口有多少辆车，交警就数多少秒，然后选一辆放行
  车越多，数得越慢，堵车越来越严重
  → 1000 辆车 = 数 1000 次 → 调度本身成为瓶颈

第二代（O(1)）：固定绿灯方向
  每个方向固定配一个交警，A 方向绿灯 1 分钟，B 方向绿灯 1 分钟
  不管 A 方向有没有车，1 分钟就换 B 方向
  → 缺点：A 方向没车时还在空等；A 方向有急救车也得等 1 分钟

第三代（CFS）：按等待时间轮流
  每辆车拿一个号码，记录等了多久
  始终选等了最久的那辆车通行
  → 公平！但如果突然有 100 辆车同时涌入，它们会挤掉已经等了很久的大货车

第四代（EEVDF）："你有 deadline，先过"
  每辆车登记"最晚什么时候必须过"
  优先让"最接近 deadline 的车"先过
  → 既公平（等久的车优先），又及时（有 deadline 的车优先）
```

---

## 问题

- 进程数增加时，调度延迟不能线性增长
- 交互进程需要快速响应，批处理需要高吞吐
- 不能让任何进程"饿死"（等太久）

---

## 各代调度器对比

```
O(n) 调度器（Linux 2.4）：
  → 每次调度遍历所有进程，找到最高优先级
  → 1000 个进程 = 遍历 1000 次
  → 进程数增加时，调度延迟线性增长

O(1) 调度器（Linux 2.6.0）：
  → 每个优先级一个运行队列，调度 O(1)
  → 问题：交互进程优先级是静态的，批处理可能"偷"走交互时间

CFS（Linux 2.6.23，2007）：
  → 红黑树，按虚拟运行时间排序
  → 完全公平，但响应延迟不理想（"湿地效应"）
  → 问题：I/O 密集型任务可能饿得太久

EEVDF（Linux 6.6，2023）：
  → 取代 CFS，成为默认调度器
  → 思想：每个进程有"eligible time"和"deadline"
  → 优先调度"最早符合条件的进程"
  → 同时照顾延迟（交互）和吞吐（批处理）
```

---

## O(n) → O(1)：固定交警的局限

**问题**：遍历所有进程找最高优先级，当进程数达到几千时，调度本身成为负担。

**类比**：交警站在路口，每过一辆车就数一遍："1、2、3...N"，找到车牌号最小的放行。车越多，数得越慢。

**解法**：为每个优先级维护一个独立的运行队列。

```
O(1) 调度器的核心数据结构：
  runqueue[140]  // 140 个优先级队列（0=最高，139=最低）
  bitset[NR_CPUS]  // 每 CPU 一个就绪队列

调度时：
  1. 找到最高的非空队列（用 bitset 找 1）→ O(1)
  2. 从该队列取一个进程 → O(1)

总复杂度：O(1)
```

**局限**：优先权是**固定**的——一个"CPU 密集型批处理进程"在队列 1 里，它就永远比队列 0 的进程优先级低，不管它等了多久。一个等了很久的重型计算任务，可能被不断涌入的轻量交互任务"饿死"。

---

## CFS（完全公平调度器）

**核心设计**：红黑树，按"虚拟运行时间（vruntime）"排序。

**类比**：每辆车有一个"等时计数器"，调度器始终选计数器数值最大的（等最久的）。

```
CFS 红黑树（按 vruntime 排序）：
                    进程B (vruntime=10ms) ← 调度器选这个（最"饿"）
                         ↓
                    进程A (vruntime=30ms)
                         ↓
                    进程C (vruntime=80ms)
                         ↓

vruntime 越小 = 越"饿" = 越应该被调度
```

**为什么叫"完全公平"**：每个进程都按 vruntime 排队，调度最"饿"的。理想情况下，所有进程最终运行的"虚拟时间"相等。

**CFS 的问题——"湿地效应"（thundering herd）**：

```
场景：1000 个进程同时等待 I/O（都是睡眠状态）
I/O 完成后：
  所有 1000 个进程的 vruntime 都很少
  同时涌入调度器
  CFS 在它们之间疯狂切换（因为都是"饿"的）
  真正的 CPU 密集型任务被挤到一边

类比：
  1000 个等了 1 分钟的人同时冲向服务窗口
  调度员让每个人只办 1 秒钟就换下一个人
  实际需要 10 分钟的大任务根本得不到完整的时间片
```

## EEVDF（Earliest Eligible Virtual Deadline First）

**核心思想**：每个任务有两个时间轴——"eligible time"（最早可被调度时间）和"deadline"（最晚必须完成时间）。

**类比**：不只是看"等了多久"，还给每辆车设定一个"最晚到达时间"。

```python
# 每个任务有两个属性
class Task:
    eligible_time   # 最早可以被调度的时间
    deadline        # 最晚必须完成的时间

# 调度决策
def pick_next():
    # 只考虑 deadline > eligible time 的任务
    # （即：已经"够格"被调度的任务）
    candidates = [t for t in runqueue if t.deadline > t.eligible_time]
    return min(candidates, key=lambda t: t.deadline)
```

### 为什么 EEVDF 更好？

| 维度 | CFS | EEVDF |
|------|-----|-------|
| 核心指标 | vruntime（谁跑得最少） | deadline（谁最紧急） |
| 延迟保证 | 无（公平但可能饿死） | 有（deadline 前必调度） |
| 交互响应 | 一般（受湿地效应影响） | 好（I/O 任务的 deadline 短） |
| 吞吐 | 高 | 高（与 CFS 相当） |
| 实现复杂度 | 中 | 中 |

### EEVDF 的本质

```
CFS 的问题：公平 ≠ 及时

CFS："让等最久的人先吃"
  → 但如果不断有人来插队（I/O 密集型频繁唤醒），
     等很久的人还是等不到

EEVDF："让最紧急的人先吃"
  → 给每个进程一个 deadline
  → 在它变得"紧急"之前先调度它
  → 不让任何进程饿死在 deadline 之前

本质上：EEVDF 在 CFS 基础上增加了一个"时间紧迫度"维度
```

## 调度器的演进规律

```
问题               →  解法                →  新问题
─────────────────────────────────────────────────────
O(n) 遍历太慢       →  每个优先级一个队列     →  优先权固定，无法动态调整
静态优先权          →  CFS 按 vruntime 公平  →  湿地效应，I/O 任务饿
公平但不及时        →  EEVDF deadline 机制   →  新问题待发现
```

**核心洞察**：没有完美的调度器——每次改进都在"公平性"、"吞吐量"、"延迟"之间做权衡。

---

## 一句话总结

> **调度器的演进，就是一部"如何在公平和及时之间找平衡"的技术进化史。**
>
> - **O(n)**：数多少个进程就遍历多少个
> - **O(1)**：固定队列，但优先级固定不变
> - **CFS**：按"等多久"排序，公平优先
> - **EEVDF**：按"多紧急"排序，公平 + 及时
