# 6.9 cgroup v2 与容器时代的资源控制

> Docker 和 Kubernetes 已经成为标准部署方式。容器需要精确的资源限制和隔离。
>
> **类比**：公寓楼里，每户（容器）都要交物业费（CPU/内存配额）。物业（cgroup）要保证：每户用电不超过额度、漏水不能影响到邻居、不能无限制地开空调。

---

## 生活场景：酒店 vs 公寓

```
酒店模式（传统虚拟机）：
  每位客人有独立的房间、独立的卫浴、独立的空调
  一个客人把浴室水管弄爆了，只有他那间房被淹
  但成本高（每个房间都要全套设施）、启动慢（开机要几分钟）

公寓模式（容器）：
  每户有自己的卧室，但共享客厅、厨房、电梯
  一户水管漏了，可能渗到楼下邻居（需要 cgroup 隔离）
  成本低（共享设施）、启动快（几秒钟）
```

---

## 问题

- 多个容器共享内核，如何保证不互相影响？
- CPU、内存、IO、PID 数量如何精确限制？
- 内存压力下，如何避免容器被 OOM Killer 误杀？

---

## 经典解法：cgroup v2

**cgroup（Control Groups）**：Linux 内核提供的资源隔离机制。

**cgroup v2**（2016 年引入，2022 年后逐步成为主流）统一了所有资源控制器。

```
cgroup 层级结构：
/sys/fs/cgroup/
├── cpu.max                    # CPU 时间和周期
├── memory.min/memory.max      # 内存限制
├── io.max                     # 磁盘 IO 限制
├── pids.max                   # PID 数量限制
└── cgroup.controllers          # 可用控制器列表
```

**类比**：物业管理系统，给每户装了独立电表、水表、燃气表。

## 内存限制实战

### Docker 层面对应

```bash
docker run \
  --memory=1g \                  # 内存上限
  --memory-swap=1g \            # swap 上限（等于 memory 表示不用 swap）
  --cpus=2 \                    # 2 个 CPU
  --cpuset-cpus="0,1" \         # 只用前两个 CPU 核
  myapp
```

### Kubernetes Pod 层面

```yaml
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: myapp
    resources:
      limits:
        memory: "1Gi"    # 上限
        cpu: "2"          # 上限
      requests:
        memory: "512Mi"   # 申请量（调度用）
        cpu: "1"          # 申请量
```

## Memory QoS（内存服务质量）

**类比**：物业给每户设置了"三级水位线"：

```
memory.min（保护线）：
  水位在这以下 → 这户的水是"受保护的"
  即使整栋楼缺水，也会优先保障这户有水

memory.low（预警线）：
  水位在这以下 → 正常服务

memory.high（警告线）：
  水位超过这里 → 开始强制回收（但不杀进程）

memory.max（硬上限）：
  水位达到这里 → 触发 OOM，必须杀掉进程

[受保护区] [优先回收区] [正常运行区] [强制回收区] [触发OOM]
  memory.min     memory.low      工作区        memory.high    memory.max
```

```bash
# 内存低水位标记（低于这个值的页面优先被回收）
echo 10240 > /sys/fs/cgroup/memory/myapp/memory.low

# 内存高水位标记（超过这个值强制回收）
echo 20480 > /sys/fs/cgroup/memory/myapp/memory.high

# 保护量（保护重要进程不被 OOM Killer 杀掉）
echo 10240 > /sys/fs/cgroup/memory/myapp/memory.min

# 设置硬上限
echo 512M > /sys/fs/cgroup/memory/myapp/memory.max
```

## CPU 限制的精度控制

```bash
# 限制到 50% CPU（相对于一个核）
echo "50000 100000" > cpu.max
# 50000/100000 = 50%

# 限制到 0.5 个 CPU
echo "50000 100000" > cpu.max

# 共享 CPU（不限制，但分配权重）
echo "1024 1024" > cpu.weight  # 默认权重 1024
echo "2048 1024" > cpu.weight   # 这个 cgroup 权重是默认的 2 倍
                                # 当系统忙碌时，这个 cgroup 获得 2 倍的 CPU 时间
```

**权重 vs 限制**：
```
cpu.max（限制）：硬上限，不能超过
cpu.weight（权重）：相对配额，系统忙碌时按权重比例分配
                    系统空闲时可以用更多

类比：
  cpu.max = 每月手机流量上限 10GB（超过就断网）
  cpu.weight = 家庭套餐分享比例（爸 60%、妈 40%）
```

## cgroup v2 的改进（相比 v1）

| 特性 | cgroup v1 | cgroup v2 |
|------|-----------|-----------|
| 层级 | 多层级（每个控制器独立） | 单一层级（所有控制器统一） |
| 通知机制 | 复杂（通过事件fd） | 统一的 notification |
| 线程模型 | 线程也可以是治理单位 | 只允许进程 |
| 内存奖励/惩罚 | 复杂 | 通过 memory.low/high 简洁表达 |
| 压力停滞 | 分散 | 统一的 memory.pressure |

```
cgroup v1 的问题：
  每个控制器（cpu、memory、io）都有自己的层级
  一个进程在 cpu 层级的 A 点，在 memory 层级的 B 点
  管理困难，资源分配不直观

cgroup v2 的改进：
  所有控制器共享同一个树形结构
  简单、直观、易于管理
```

## 为什么容器需要 cgroup + namespace？

**类比**：

```
cgroup = 资源限制（能用什么、最多用多少）
  "每户每月最多用 10 度电、5 吨水"

namespace = 视图隔离（能看到什么）
  "每户只能看到自己家的阳台，看不到邻居家"
  "每户觉得自己是 1 号住户（PID）"

cgroup + namespace = 容器
  容器以为自己是独立的"虚拟服务器"
  实际上共享宿主机的内核，但资源被精确限制
```

## OOM Killer 与容器的交互

**问题**：当容器内的进程被 OOM Killer 杀掉时，是容器内的进程全被杀掉，还是只有那一个进程？

```
场景：容器设置了 --memory=512m

情况 1：进程自己触发了 cgroup OOM
  → cgroup 内存达到上限
  → 容器内所有进程收到 SIGKILL
  → docker ps 显示 Exited (137)

情况 2：系统整体 OOM（宿主机内存耗尽）
  → OOM Killer 基于 oom_score 选择进程
  → 可能杀掉容器内的某个进程，不一定是触发 OOM 的那个
```

**防御策略**：
```yaml
# Kubernetes: 设置 Pod 的 OOMKillDisable = false
# 并合理设置 memory limits
spec:
  containers:
  - name: myapp
    resources:
      limits:
        memory: "512Mi"
```

---

## 一句话总结

> **cgroup v2 的本质，是让共享内核的容器之间"公平"且"可预测"地分配资源——每户交多少用多少，一个住户出问题不影响整栋楼。**
>
> - **memory.min/low/high/max**：内存的"保护-预警-工作-强制回收-OOM"五级水位
> - **cpu.max/cpu.weight**：CPU 的"硬上限"和"相对权重"
> - **cgroup + namespace**：限制资源 + 隔离视图 = 容器
