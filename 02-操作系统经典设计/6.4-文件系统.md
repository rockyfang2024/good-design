# 6.4 文件系统：如何持久化存储

> 磁盘上要存几十亿个文件，每个文件有名字、大小、时间戳、内容。怎么组织？
>
> **类比**：想象一个没有抽屉、没有标签、全靠记忆的仓库——你放进去 1000 个箱子，一年后要找一个螺丝刀，你还记得放在哪吗？文件系统，就是给磁盘这个"超大仓库"设计了一套"智能标签系统"。

---

## 生活场景：图书馆 vs 杂乱仓库

```
杂乱仓库（无文件系统）：
  老板："我有一批货要存。"
  仓库管理员："行，往角落一扔吧。"
  老板："我怎么找回来？"
  管理员："你自己记着是哪堆。"

  问题：东西越多越乱，丢东西、找不到东西、空间利用率极低

图书馆（文件系统）：
  每一本书有编号（ISBN）、书架号、层号
  你说"要借《操作系统设计》"，图书管理员查系统 → 找到位置 → 去拿
  所有书都有序排列，空间高效，不会"找不到"
```

---

## 问题

- 文件名变长、变短 → 不能预分配固定大小
- 删除文件 → 产生空洞，不能浪费空间
- 目录层级深 → 需要高效查找
- 突然断电 → 不能丢数据

---

## 经典解法：inode + 块组

### 先问一个问题：文件内容存在磁盘哪里？

**朴素的想法**：文件 A 占 0-99 号扇区，文件 B 占 100-199 号扇区。

**问题**：
1. 文件 A 删掉了，空出 0-99，但 B 不能自动挪过去
2. 文件 A 长大了，需要更多空间，但 100-199 已经被 B 占了
3. 空间利用率低，到处是碎片

**解决思路**：不给文件连续空间，而是给文件一个"指向磁盘块的指针列表"。文件散布在磁盘任意位置，需要时逐块读。

---

### inode（索引节点）

**类比**：每本书在图书馆系统里有一个"卡片目录"。

```
inode = 图书卡片目录
  包含：
    - 这本书的元数据（谁写的、几页、什么时候入库）
    - 书在哪个书架（磁盘块指针列表）

磁盘上的实际书页 = 数据块
索引卡片（inode）= 指向实际书页的指针列表
```

```
磁盘布局（一个楼层）：
┌─────────┬────────────┬─────────────────┬────────────────┐
│ 楼层图   │ 块组描述符  │  索引节点区        │  数据块区       │
│(Super   │ (这片区域   │  (inode 表)       │  (实际存文件   │
│ Block)  │ 有几个空闲) │                   │   内容的地方)   │
└─────────┴────────────┴─────────────────┴────────────────┘

inode 结构（ext2/ext3/ext4）：
┌──────────────┬───────────────────────────────────────┐
│ 元数据       │ 数据块指针                              │
├──────────────┼───────────────────────────────────────┤
│ mode         │ block[0-11]  ← 12 个直接块（12 × 4KB）│
│ uid          │ block[12]    ← 单间接块（1024 个块）   │
│ size         │ block[13]    ← 双间接块                 │
│ atime/mtime  │ block[14]    ← 三间接块                 │
│ links        │                                      │
│ ...          │                                      │
└──────────────┴───────────────────────────────────────┘
            最大文件 ≈ 16KB（直接）+4GB（间接）≈ 4TB+
```

**为什么用 inode 而非连续分配**：

```
连续分配（问题版）：
  文件 A 占 0-9 号块，文件 B 占 10-19 号块
  → 删了 A，空出 0-9，B 不能自动长大填进去 → 碎片化

inode（解决版）：
  文件是 block 指针的集合
  → 文件可以散布在磁盘任何位置，按需分配
  → 删除文件只是释放指针指向的块，不影响其他文件
  → 文件可以随时变大，只要磁盘有空闲块就行
```

### 日志文件系统（Journaling）——"先记账后干活"

**问题**：写文件时突然断电，可能只写了一半。磁盘上留下"半成品"，文件系统进入不一致状态。

**类比**：会计做账前先把要做的操作写在纸上，确认了再执行。
- **先记账**：我要从 A 账户转 100 到 B 账户，先把"转账 100"写在纸上
- **再执行**：执行完，确认纸条上的任务划掉
- **崩溃恢复**：开机时检查纸条，发现有未完成的操作 → 撤销或重做

```
正常文件系统写入（危险）：
  直接写磁盘 → 可能写一半断电 → 数据和索引不一致

日志文件系统写入（安全）：
  1. 把"要干什么"先写到日志区（顺序写入，很快）
     - TxB（事务开始）：我要改 inode 5，把数据块 100 改成这些内容
     - [新数据内容]
     - TxE（事务结束）

  2. 日志落盘后（表示"操作已记录"），再去实际修改数据

  3. 实际修改完成后，标记这条日志"已完成"

崩溃恢复时：
  检查日志 → 发现有条未完成的事务 → 重做（REDO）或撤销（UNDO）
  → 文件系统恢复到一致状态
```

**代表系统**：ext3/ext4, NTFS, JFS, XFS 都使用日志。

## 扩展：VFS（虚拟文件系统层）

**问题**：Linux 要同时支持 ext4、XFS、Btrfs、NFS、CIFS……几十种文件系统。每种文件系统的"内部语言"不同。怎么让应用程序用统一的 API 访问所有？

**类比**：全世界有 200 种语言，但外交官只需要会"英语+手语"就能沟通——因为有翻译官。

```
                应用程序（说英语）
                       │
              open() read() write() mkdir()  ← 统一的 POSIX API
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
    ┌──────────┐              ┌──────────┐              ┌──────────┐
    │   ext4   │              │   XFS    │              │   NFS    │
    │ 英文翻译  │              │ 法语翻译  │              │  中文翻译 │
    └──────────┘              └──────────┘              └──────────┘
          ▲                         ▲                        ▲
          └────────────────────────┴────────────────────────┘
                               ▼
                     VFS（虚拟文件系统层）
                       —— 同声传译部门 ——
```

**VFS 的四个核心对象**：

```c
struct super_block    // 整个"图书馆"的元数据（有多少书架、总容量）
struct inode         // 一本"书"的元数据（作者、页数、存放位置）
struct dentry        // "图书索引卡"（书名→书的映射，路径解析）
struct file          // "某个人正在看的某一页"（进程打开的文件实例）

// 每个文件系统必须实现一组"翻译函数"
struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int     (*open)(struct inode *, struct file *);
    // ...
};
```

**dentry 缓存（目录项缓存）**：

```
路径解析 /home/ubuntu/file.txt：

第一步：查 dentry 缓存
  "/home/ubuntu/file.txt" 可能在缓存里 → 直接命中 → 不用逐级找了

第二步：缓存未命中，逐级查 inode
  /         → root inode
  home      → root inode 的 dentry → home inode
  ubuntu    → home inode 的 dentry → ubuntu inode
  file.txt  → ubuntu inode 的 dentry → file inode

第三步：把每一级的映射缓存到 dentry
  下次访问 "/home/ubuntu/" 任何文件，直接命中
```

## 扩展：文件系统的"快捷方式"

### 硬链接 vs 软链接

```
硬链接：同一本书的另一个书架编号
  - inode 相同（同一本书）
  - 删除一个链接，只要还有链接，书就在
  - 不能跨文件系统（不能链接到另一个仓库的书）
  - ln file1 file2

软链接（符号链接）：便利贴上的"请去 B 仓库第三排找"
  - inode 不同（便利贴本身是一张小纸片）
  - 只是个指针，指向另一个路径
  - 可以跨文件系统
  - 目标删了，链接就断了（ dangling 指针）
  - ln -s target link_name
```

### 命名管道（FIFO）——"单向传递窗口"

**类比**：医院挂号窗口，患者把单子递进去，护士在里面处理。窗口这边只能递，那边只能接。

```
进程 A（生产者）                        进程 B（消费者）
      │                                       ▲
      │ write("化验单")                        │
      ├───────────────── pipe ─────────────────┤
      │                                       │
```

```c
// 创建管道
int pipefd[2];
pipe(pipefd);  // pipefd[0]=读端, pipefd[1]=写端

// 写
write(pipefd[1], "hello", 5);

// 读
read(pipefd[0], buf, 5);
```

**管道 vs Socket**：
```
管道：像水流，没有边界，流进来的是什么顺序就是什么顺序
Socket：像包裹，每个包裹都有自己的标签和边界
```

---

## 一句话总结

> **文件系统的本质，是把磁盘这个"能存 0 和 1 的大平面"变成"有结构、可查找、不怕断电"的文件仓库。**
>
> - **inode**：书的索引卡，记录书在哪（磁盘块指针）
> - **日志**：先记账后干活，保证崩溃后能恢复
> - **VFS**：让不同文件系统"说同一种语言"，应用程序不用关心底层细节
> - **dentry 缓存**：把常用的"路径→文件"映射记在内存里，加速查找
