# 6.3 同步互斥：让并发安全

> 两个进程同时操作共享资源（计数器、链表、文件），会发生什么？
>
> **类比**：两个人同时在共享的 Google Doc 里编辑同一段文字，一个在打字，一个在删字。结果往往是"你打的字被他的删除覆盖了"，或者"你们谁都不知道最终写了什么"。

---

## 生活场景：两个人同时改同一份报告

```
场景：
小王和小张都在改一份季度报告，都开着同一个 Word 文档。

❌ 出问题的流程：
t=0s: 小王的光标在第3段，光标位置=第3段开头
t=1s: 小张的光标也在第3段（两人同时打开）
t=2s: 小王输入"收入增长了20%"（在第3段中间打字）
t=3s: 小张删除了第3段（他想删掉旧数据）
t=4s: 小王的"收入增长了20%"跟着第3段一起被删了
t=5s: 小王："我刚才打的字呢？！"

这就是 Race Condition（竞态条件）——两人对同一个资源
的访问顺序不确定，最终结果取决于"谁最后动了手"。
```

**代码里的 Race Condition**：

```python
# 两个进程同时执行 count += 1
# count 初始值 = 0

# 进程 A: read count → 0
# 进程 B: read count → 0     （在 A 写入之前读了）
# 进程 A: write count → 1   (基于旧的 0)
# 进程 B: write count → 1   (基于旧的 0) ← 错误！应该是 2
```

---

## 经典解法

### 方案一：互斥锁（Mutex）——"厕所门锁"

**类比**：公共厕所只有一把钥匙。想进去？先拿钥匙（acquire），出来时还钥匙（release）。

```
厕所门口（共享资源：马桶）
  │
  ├─ 门锁（Mutex）
  │   ├─ 有人持钥匙 → 锁门 → 其他人等在外面
  │   └─ 持钥匙人出来 → 还钥匙 → 锁开 → 下一个人进
  │
  └─ 等的人排队（等待队列）
```

```python
import threading

lock = threading.Lock()  # 只有一把钥匙

def 有人要用厕所():
    lock.acquire()       # 拿钥匙（等在外面的就阻塞在这）
    try:
        # 临界区：只有一个人能在这里
        count += 1
    finally:
        lock.release()   # 还钥匙，下一个人可以进了

# 线程 A（必须等 A 出来）
有人要用厕所()

# 线程 B（等 A 释放锁后才会执行）
有人要用厕所()
```

**Mutex 的实现（硬件支持）**：

```c
// 原子操作：Test-and-Set（测试并设置）
// 硬件保证这一条指令执行过程不会被中断
bool test_and_set(bool *target) {
    bool old = *target;   // 读
    *target = true;       // 写
    return old;           // 返回旧值
}

// 自旋锁实现
void lock(bool *mutex) {
    while (test_and_set(mutex) == true) {
        // 锁已经被持有了，我就原地等（自旋）
        // 就像等厕所的人站在门口转圈圈
    }
}

void unlock(bool *mutex) {
    *mutex = false;  // 释放锁
}
```

**为什么普通读/写不行**：

```c
// 这不是原子操作（两条指令）
old = *mutex;      // 其他 CPU 核心可能在这两步之间看到中间状态
*mutex = true;

// 就像：
// 第一步：把门把手拧到"开"的位置
// 第二步：推门
// 如果两人同时做第一步，都看到"开"，都推门，就撞上了
```

### 方案二：信号量（Semaphore）——"多人厕所的多把钥匙"

**Mutex 的问题**：只有一把钥匙，同时只能有一个人用。

**信号量的类比**：女公共厕所，有 10 把钥匙（5个蹲位+5个马桶）。来一个人拿一把钥匙，进去了就把钥匙拿走。钥匙拿完了？后面的人在外面等。

```python
from threading import Semaphore

# 10 把钥匙 = 最多同时 10 个人用
pool = Semaphore(10)

def handle_request():
    pool.acquire()   # 拿钥匙（没钥匙就等）
    try:
        # 处理请求
    finally:
        pool.release()  # 还钥匙，下一个人可以进
```

**信号量的实现**：

```c
struct Semaphore {
    int value;           // 剩余钥匙数量
    Queue waiters;       // 等在外面的队伍
};

// P 操作（Proberen = 测试荷兰语）
void P(Semaphore *s) {  // 拿钥匙
    atomic_decrement(&s->value);  // 原子减 1
    if (s->value < 0) {
        block_current_process(s->waiters);  // 没钥匙，阻塞
    }
}

// V 操作（Verhogen = 增加荷兰语）
void V(Semaphore *s) {  // 还钥匙
    atomic_increment(&s->value);
    if (s->value <= 0) {
        wake_one_process(s->waiters);  // 叫醒一个等的人
    }
}
```

### 方案三：读写锁——"图书馆的自习室"

**场景**：自习室可以同时有多人看书（读），但有人要写字（写）时，整个房间只能有他一个人。

```python
import threading

rwlock = threading.RWLock()

def 看书():
    with rwlock.read_lock():  # 读者可以并行
        read_data()

def 写字():
    with rwlock.write_lock():  # 写者独占
        write_data()
```

### 死锁的四个必要条件（破坏任一即可）

**类比**：十字路口，两辆车同时驶入：
- 车 A 从南向北，占据了路中央
- 车 B 从东向西，占据了路中央
- 两车都不能动，都等对方让路 → 死锁

```
死锁的四个条件（缺一不可）：

1. 互斥：资源只能被一个人用
   → 十字路口不能双向通行（无法破坏）

2. 持有并等待：拿了资源 A，还在等资源 B
   → 车 A 占了路南，还在等路东
   → 破坏：要么一开始就把两条路都占了，要么不占就走

3. 不可抢占：资源不能被抢走
   → 破坏：交警可以直接拖走其中一辆车

4. 循环等待：A 等 B，B 等 A
   → 破坏：规定所有车必须"先占南边再占东边"，不能半路换道
```

**预防死锁的代码原则**：
```python
# ❌ 危险写法（可能死锁）
lock_a.acquire()
lock_b.acquire()
do_something()
lock_b.release()
lock_a.release()

# ✅ 安全写法（固定顺序）
lock_a.acquire()
lock_b.acquire()  # 永远按同样顺序加锁
do_something()
lock_b.release()
lock_a.release()
```

### 方案四：RCU（Read-Copy-Update）——"边改边登报"

**适用场景**：读多写少（1000 次读 + 1 次写）。

**类比**：报纸改版
- **旧读者**：继续看旧报纸，不受影响
- **新读者**：自动看到新报纸
- **编辑**：等所有旧读者看完后，回收旧报纸

```python
# 读：完全无锁，极快
def read():
    return data  # 直接读，永远不会被阻塞

# 写：复制+替换
def write(new_value):
    old = data
    new_data = new_value
    # 等所有正在读的读者都读完（旧报纸都用完了）
    # 然后释放 old
    defer_free(old)
```

**本质**：读者的"快照一致性"由 RCU 保证——写者创建新版本，读者各看各的，不打架。

## 扩展：内核同步原语

**问题**：内核里同时有中断处理、软中断、进程上下文——同一段代码可能从不同"角度"被调用。怎么保证安全？

### 五种上下文的"脾气"

```
进程上下文（普通员工）
  → 可以睡觉（等锁）、可以被打断
  → 比如：应用程序的系统调用

中断处理（快递员）
  → 不能睡觉，必须快速完成
  → 来了就要处理，处理完就走
  → 只能拿自旋锁

软中断（外卖骑手）
  → 不能睡觉，高频率事件（网络包、块设备）
  → 也只能用自旋锁

tasklet（跑腿小弟）
  → 基于软中断，不能睡觉
  → 优先级介于中断和进程之间

工作队列（快递柜暂存区）
  → 可以睡觉，在进程上下文执行
  → 可以拿信号量
```

### 自旋锁 vs 信号量选择

```c
// 规则：
// 1. 中断上下文 → 只能用自旋锁（不能睡觉！）
// 2. 进程上下文且可能睡眠 → 信号量
// 3. 进程上下文且不能睡眠 → 自旋锁

// 中断上下文获取锁（自动禁用该 IRQ，防止嵌套中断）
spin_lock_irqsave(&my_lock, flags);
// ... 临界区 ...
spin_unlock_irqrestore(&my_lock, flags);

// 进程上下文获取锁
spin_lock(&my_lock);
// ... 临界区 ...
spin_unlock(&my_lock);

// 可以睡眠的进程上下文
down(&my_semaphore);  // 获取信号量（拿不到就睡）
// ... 临界区 ...
up(&my_semaphore);
```

---

## 一句话总结

> **并发安全的关键，是给共享资源加一把"锁"——但锁的选择（Mutex / Semaphore / RCU）取决于场景：谁在用、多久用一次、是读多还是写多。**
>
> - **Mutex**：一把钥匙，进门拿、出门还
> - **Semaphore**：多把钥匙，控制同时使用的数量
> - **RCU**：读写分离，写的人慢（要等旧读者散去），读的人快（永远不阻塞）
> - **死锁**：4 个条件缺一不可，破坏任一即可破局
