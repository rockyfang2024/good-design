# 6.3 同步互斥：让并发安全

> 两个进程同时操作共享资源（计数器、链表、文件），会发生什么？

---

## 问题

```
进程 A: read count → 5
进程 B: read count → 5
进程 A: write count → 6   (基于旧的 5)
进程 B: write count → 6   (基于旧的 5)  ← 错误！应该是 7
```

这是经典的 **Race Condition（竞态条件）**。

---

## 经典解法

### 互斥锁（Mutex）

```python
lock = Mutex()

def critical_section():
    lock.acquire()     # 拿锁，阻塞等待
    count += 1         # 临界区：同时只有一个进程能进来
    lock.release()     # 放锁

critical_section()     # 进程 A（必须等 A 释放）
critical_section()     # 进程 B
```

**Mutex 的实现（硬件支持）**：

```c
// TAS (Test-and-Set) 指令 - 原子操作
bool test_and_set(bool *target) {
    bool old = *target;
    *target = true;
    return old;
}

// 自旋锁实现
void lock(bool *mutex) {
    while (test_and_set(mutex) == true) {
        // 忙等待（自旋）
    }
}

void unlock(bool *mutex) {
    *mutex = false;
}
```

**为什么不能直接用普通读/写**：

```c
// 这不是原子操作（两条指令）
old = *mutex;
*mutex = true;  // 其他 CPU 核心可能在这两步之间看到中间状态
```

---

### 信号量（Semaphore）

Mutex 只能被一个进程持有。**信号量**可以控制 N 个资源：

```python
from threading import Semaphore

# 10 个连接池，信号量控制并发上限
pool = Semaphore(10)

def handle_request():
    pool.acquire()
    try:
        # 处理请求
    finally:
        pool.release()
```

**Semaphore 的实现**：

```c
struct Semaphore {
    int value;
    Queue waiters;      // 等待队列
};

void P(Semaphore *s) {  // wait / acquire
    atomic_decrement(&s->value);
    if (s->value < 0) {
        block_current_process(s->waiters);
    }
}

void V(Semaphore *s) {  // signal / release
    atomic_increment(&s->value);
    if (s->value <= 0) {
        wake_one_process(s->waiters);
    }
}
```

**注意**：`P()` 和 `V()` 本身必须是**原子操作**——在多核上需要硬件指令（CAS、LL/SC）配合。

---

### 读写锁

```python
# 读可以并发（多个读者不冲突）
# 写必须独占（写者与所有读者互斥）
rwlock = ReadWriteLock()

def read_data():
    with rwlock.read_lock():
        return data

def write_data():
    with rwlock.write_lock():
        data = new_data
```

---

### 死锁的四个必要条件（破坏任一即可）

```python
# 1. 互斥：资源只能被一个进程占用
#    → 无法破坏（有些资源本质上是互斥的）

# 2. 持有并等待：进程持有资源同时请求更多
#    → 破坏：要么一次性申请所有资源，要么不持有时再申请

# 3. 不可抢占：已分配资源不能被强制夺走
#    → 破坏：允许内核强制剥夺资源

# 4. 循环等待：形成 P1→P2→...→Pn→P1 的等待链
#    → 破坏：给所有资源编号，必须按顺序申请（资源有序化）
```

---

### RCU（Read-Copy-Update）

对于读多写少场景：

```python
# 读：完全无锁，极快
def read():
    return data  # 直接访问，无需加锁

# 写：不是原地修改，而是复制+替换
def write(new_value):
    old = data
    new_data = new_value
    defer_free(old)  # 在 grace period 后释放旧数据
```

**核心思想**：读操作永远不被阻塞（无锁读）；写操作创建副本，替换指针，所有读者读到新版本后再释放旧版本。

Linux 内核大量使用 RCU 来保护链表、树等数据结构。

## 扩展：内核中的锁与无锁数据结构

**问题**：内核里同时有中断处理、软中断、进程上下文——同一段代码可能从不同上下文被调用。怎么保证同步安全？

### Linux 内核的五种上下文

```
进程上下文（process context）→ 可以睡眠，可以获取信号量
  ↑
中断处理（interrupt handler）→ 不可睡眠，只能用自旋锁
软中断（softirq）→ 不可睡眠，用于高频率事件（网络、块设备）
tasklet→ 基于软中断，不能睡眠
工作队列（workqueue）→ 可以睡眠，在进程上下文执行
```

### 自旋锁 vs 信号量选择

```c
// 规则：
// 1. 中断上下文 → 只能用自旋锁
// 2. 进程上下文且可能睡眠 → 信号量
// 3. 进程上下文且不能睡眠 → 自旋锁

// 中断上下文获取锁（自动禁用该 IRQ）
spin_lock_irqsave(&my_lock, flags);
// ... 临界区 ...
spin_unlock_irqrestore(&my_lock, flags);

// 进程上下文获取锁
spin_lock(&my_lock);
// ... 临界区 ...
spin_unlock(&my_lock);

// 可以睡眠的进程上下文
down(&my_semaphore);  // 获取信号量（可能睡眠）
// ... 临界区 ...
up(&my_semaphore);
```

### Linux 内核的无锁数据结构

```c
// 1. percpu 计数器（无锁，每个 CPU 独立计数）
DEFINE_PER_CPU(long, my_counter);

// 2. RCU（读多写少场景）
rcu_read_lock();
struct my_struct *p = rcu_dereference(global_ptr);
// 使用 p ...
rcu_read_unlock();
// writer: rcu_assign_pointer() + synchronize_rcu()

// 3. x86 原子指令
atomic_inc(&counter);
atomic_add_return(5, &counter);
cmpxchg(&old_val, new_val, ptr); // CAS
```
