# 6.2 内存管理：虚拟内存

> 物理内存只有 4GB，但运行了 100 个进程。怎么让每个进程都觉得拥有完整的地址空间？

---

## 问题

- 物理内存只有 4GB，但运行了 100 个进程
- 每个进程都可能崩溃，不能让一个进程的 bug 影响到其他进程
- 程序大小可能超过物理内存（部分加载）
- 需要让进程觉得自己有"连续完整"的地址空间

---

## 经典解法：虚拟内存 + 分页

### 虚拟地址空间（每个进程独立的）

```
0x00000000  ┌─────────────────┐
            │     代码段       │ 0x400000
            ├─────────────────┤
            │     数据段       │
            ├─────────────────┤
            │     堆（向上生长）│ ← malloc 分配这里
            │                 │
            │    （空闲）      │
            │                 │
            │    栈（向下生长）│ ← 函数调用
0xBFFFFFFF  └─────────────────┘
```

### 分页机制

物理内存被切成固定大小的"页"（通常 4KB），通过页表映射：

```
虚拟页 0  →  物理页 7
虚拟页 1  →  物理页 3
虚拟页 2  →  [不在内存，在磁盘 swap 区]
虚拟页 3  →  物理页 1
```

### 页表条目（PTE）结构

```c
struct PageTableEntry {
    uint8_t  present: 1;    // 页面是否在内存
    uint8_t  writable: 1;   // 是否可写
    uint8_t  user: 1;        // 用户态可访问？
    uint16_t physical_page;  // 物理页号
    uint8_t  accessed: 1;   // 被访问过（用于置换）
    uint8_t  dirty: 1;      // 被修改过（换出时需要写回）
    // ...
};
```

## 页置换算法

当物理内存满了，需要把某个页换到磁盘。经典的算法：

### LRU（最近最少使用）

```python
# 每次访问页，把它移到"最近使用"队列的末尾
# 需要淘汰时，淘汰队列头（最久未使用的）
memory_pages = ["A", "B", "C"]  # 最左=最久未用

def access(page):
    memory_pages.remove(page)
    memory_pages.append(page)  # 移到末尾

def evict():
    return memory_pages.pop(0)  # 淘汰最老的
```

**问题**：LRU 需要维护有序队列，复杂度 O(n)；且在某些访问模式（顺序扫描）下性能极差。

### CLOCK（第二次机会）

```python
# 用一个环形缓冲区和"使用位"
# 指针循环遍历：
#   - 如果使用位=1 → 清零，移到下一页（给第二次机会）
#   - 如果使用位=0 → 淘汰
pages = ["A", "B", "C", "D"]  # 使用位=[1, 0, 1, 0]
pointer = 0

def find_evict():
    while True:
        if pages[pointer].used:
            pages[pointer].used = 0
            pointer = (pointer + 1) % len(pages)
        else:
            return pointer
```

**为什么用 CLOCK 而不是 LRU**：
- LRU 需要每次访问都更新队列（代价高）
- CLOCK 只需要置位/清位，指针顺时针移动，O(1)

### 工作集模型

```python
# "工作集" = 最近 W 次访问的页面集合
# 如果一个页面不在工作集里，很快就会被淘汰

def should_evict(page, working_set):
    return page not in working_set
```

**核心洞察**：程序有局部性——当前用到的数据/代码，很快会再用到。LRU/CLOCK 就是利用这个特性。

## TLB（Translation Lookaside Buffer）

页表查找是 O(1) 但有 2-3 次内存访问，代价高。加一个缓存：

```
CPU 想要访问虚拟地址 0x4040
    │
    ├─ TLB 查找（硬件缓存，并行）
    │   ├─ 命中 → 直接拿到物理地址（1 个周期）
    │   └─ 未命中 → 查页表 → 填充 TLB → 返回
    │
    ▼
物理内存访问
```

TLB 命中率通常 > 95%，所以实际效果接近 O(1)。

## 扩展：NUMA-aware 内存管理

**问题**：多路服务器中，CPU 和内存被分成多个"节点"，访问本地内存比访问远程内存快 2-3 倍。怎么让进程尽量用本地内存？

**NUMA 架构**：

```
        CPU 0           CPU 1           CPU 2           CPU 3
      [核心]          [核心]          [核心]          [核心]
         │               │               │               │
      [内存节点0]     [内存节点1]     [内存节点2]     [内存节点3]
       64GB            64GB            64GB            64GB
         │               │               │               │
         └───────────────┴───────────────┴───────────────┘
                        QPI/InfinityBand 互联
```

**Linux NUMA 策略**：

```bash
# 查看 NUMA 拓扑
numactl --hardware

# 查看当前进程的 NUMA 亲和
numactl --show

# 把进程绑定到特定节点
numactl --membind=0 --cpunodebind=0 python script.py

# 自动选择本地节点
numactl --localalloc python script.py
```

**透明大页（Transparent Huge Pages）**：

```bash
# 查看大页配置
cat /sys/kernel/mm/transparent_hugepage/enabled

# 优点：减少页表层级，降低 TLB miss
#   4KB 页：虚拟地址空间 48 位 → 4 级页表
#   2MB 页：只需 3 级页表，TLB 条目更少
#
# 缺点：内存碎片化、khugepaged 扫描开销
# 生产环境建议：madvise 模式下启用
```

## 扩展：内存压缩与 OOM Killer

**问题**：内存耗尽时，系统不能直接崩溃。需要优雅地回收内存或杀掉不重要的进程。

### 内存回收层级（从轻到重）

```
层级 1：kswapd 守护进程（异步回收）
  → 当可用内存低于 watermark_high，开始kswapd
  → 扫描不活跃的 LRU 链表，尝试换出页面
  → 不阻塞任何进程

层级 2：直接内存回收（direct reclaim）
  → 当进程分配内存但没有足够可用页
  → 进程自己触发回收（可能阻塞）
  → 导致性能抖动（application stalls）

层级 3：OOM Killer
  → 所有回收手段失败
  → Linux 选择"最该死"的进程杀掉
  → dmesg 里可以看到 "Out of memory: Killed process ..."
```

### OOM Score 与 oom_score_adj

```bash
# 查看进程 OOM score（越高越容易被杀）
cat /proc/12345/oom_score

# 调整 OOM 偏好（-1000 到 +1000）
echo -1000 > /proc/12345/oom_score_adj  # 永远不杀
echo +1000 > /proc/12345/oom_score_adj  # 优先杀
```

### OOM Killer 选择算法

```python
# Linux 6.1+ 使用 "能量感知" 算法
def select_victim():
    score = oom_score_adj + resident_pages / 1000
    score += pgmajfault_delta
    score += vm_committed_anon

    if is_root_process(pid):
        score *= 0.9

    return process_with_highest_score
```

### 防御 OOM 的策略

```bash
# 容器层面：设置 memory limit，让容器在达到限制时触发 cgroup OOM
docker run --memory=512m --memory-swap=512m myapp
# 达到 limit 时，容器内的进程收到 SIGKILL（更可预测的行为）
```
