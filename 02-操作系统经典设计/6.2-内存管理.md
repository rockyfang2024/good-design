# 6.2 内存管理：虚拟内存

> 物理内存只有 4GB，但运行了 100 个进程。怎么让每个进程都觉得拥有完整的地址空间？
>
> **类比**：就像一个小区只有 1000 个快递柜（物理内存），但住了 500 户（进程），每户都觉得自己有一个专属的 100 格快递柜。物业（操作系统）用一套"虚拟柜号→真实柜号"的映射表，让每户都能自由用自己的柜子，还不怕某户乱拿别人家的东西。

---

## 生活场景：小区快递柜

```
物业公告：
  每户的"虚拟柜号"从 1-100 编号，但真实的物理柜只有 1000 个。
  怎么分配？

映射表（就像页表）：
  张三家的 1号虚拟柜 → 物理柜 #201（真实位置）
  张三家的 2号虚拟柜 → 物理柜 #87
  李四家的 1号虚拟柜 → 物理柜 #203（注意：跟张三的不同！）
  王五家的 1号虚拟柜 → 还没分配，在硬盘的"快递暂存区"

好处：
  ✅ 每户都以为自己有 100 个专属柜子
  ✅ 某户快递柜满了，可以把不常用的柜子里的东西临时挪到"快递暂存区"（swap）
  ✅ 某户有人乱拿东西，也只能拿自己家的虚拟柜（隔离）
  ✅ 快递柜物理上可以放在任意位置，不用连续
```

---

## 问题

- 物理内存只有 4GB，但运行了 100 个进程
- 每个进程都可能崩溃，不能让一个进程的 bug 影响到其他进程
- 程序大小可能超过物理内存（部分加载）
- 需要让进程觉得自己有"连续完整"的地址空间

---

## 经典解法：虚拟内存 + 分页

### 虚拟地址空间（每个进程独立的）

```
0x00000000  ┌─────────────────┐
            │     代码段       │ ← 程序的"操作手册"
            ├─────────────────┤
            │     数据段       │ ← 程序的"工作台"
            ├─────────────────┤
            │     堆（向上生长）│ ← malloc 分配这里，像拼图块越摆越高
            │                 │
            │    （空闲）      │ ← 可用的虚拟空间
            │                 │
            │    栈（向下生长）│ ← 函数调用，像叠盘子越叠越低
0xBFFFFFFF  └─────────────────┘
```

**类比**：
```
代码段 = 你家的"功能手册"（每页写着一个功能）
数据段 = 你家的"工作台"（放着当前用的工具和材料）
堆      = 你家厨房的"菜板"（用完一块砧板切菜，放旁边，再拿一块新的）
栈      = 你家厨房的"碗碟架"（刚洗完的碗碟往最上面叠，用的时候从最上面拿）
```

**为什么堆向上长、栈向下长**？就像厨房里：
- 切菜区（堆）：砧板从厨房中间往窗户方向摆，越摆越远
- 碗碟区（栈）：从厨房中间往门口方向叠，越叠越低
这样两边"对着扩"，中间空出来的就是共享的灵活空间。

---

### 分页机制

**类比**：把小区快递柜标准化成固定大小（4KB），每个柜子有一个编号。

```
虚拟页（你家的虚拟柜号）    物理页（真实的物理柜）
虚拟页 0  →  物理页 7        张三家虚拟 1 号 → 201号柜
虚拟页 1  →  物理页 3        张三家虚拟 2 号 → 87号柜
虚拟页 2  →  [不在柜子，在地下室暂存区]  ← 还没分配到真实柜位
虚拟页 3  →  物理页 1        李四家虚拟 1 号 → 203号柜（跟张三家完全独立！）
```

**分页的好处**：
1. **不要求物理连续**：虚拟空间连续的 10 个页，可以散落在物理内存任意位置
2. **按需分配**：虚拟页 2 不访问，就不会分配物理页
3. **进程隔离**：张三家的虚拟页 1 映射到 201，李四家的虚拟页 1 映射到 203——虽然都是"虚拟1号柜"，但实际位置完全不同

### 页表条目（PTE）结构

```c
struct PageTableEntry {
    uint8_t  present: 1;    // 这个柜子现在有没有东西（在不在内存）
    uint8_t  writable: 1;   // 能不能往里面放东西
    uint8_t  user: 1;        // 普通住户能不能用（还是只有物业能用）
    uint16_t physical_page;  // 真实的物理柜号是多少
    uint8_t  accessed: 1;    // 最近有没有人开过这个柜子（回收依据）
    uint8_t  dirty: 1;      // 里面的东西有没有被改过（换出时要写回）
};
```

## 页置换算法

当物理内存满了，需要把某个页换到磁盘。经典的算法：

### LRU（最近最少使用）

**类比**：当快递柜满了，快递员会找**最久没人打开过**的那个柜子，把新快递塞进去。

```python
# 每次有人打开柜子，把它移到"最近使用"队列的末尾
# 需要淘汰时，淘汰队列头（最久未使用的）
memory_pages = ["A柜", "B柜", "C柜"]  # 最左=最久未用

def open_cabinet(cabinet):
    cabinets.remove(cabinet)
    cabinets.append(cabinet)  # 最近用过，放最后

def find_victim():
    return cabinets.pop(0)  # 淘汰最老的那个
```

**问题**：LRU 需要维护有序队列，复杂度 O(n)；且在某些访问模式（顺序扫描）下性能极差。

> **LRU 的致命问题**：想象你看一本 1000 页的书，每页只翻 1 秒，翻完全书。你其实每页都"最近用过"，但 LRU 会认为每页都很重要——结果缓存失效，效率极低。

### CLOCK（第二次机会）

**类比**：快递员不是找最久没开的柜子，而是拿个指针**绕着快递柜转一圈**：
- 发现柜子最近有人用过（使用位=1）→ 擦掉标记，继续转
- 发现柜子最近没人用过（使用位=0）→ 选它，放新快递

```python
# 环形缓冲区和"使用位"
pages = [
    {"id": "A", "used": 1},  # 最近用过
    {"id": "B", "used": 0},  # 很久没用
    {"id": "C", "used": 1},  # 最近用过
    {"id": "D", "used": 0},  # 很久没用
]
pointer = 0

def find_evict():
    while True:
        if pages[pointer]["used"]:
            pages[pointer]["used"] = 0  # 清0，继续转
            pointer = (pointer + 1) % len(pages)
        else:
            return pointer  # 找到淘汰目标
```

**为什么比 LRU 更实用**：
- LRU：每次开柜子要移动整个队列 O(n)
- CLOCK：每次只置位/清位，指针移动，O(1)

## TLB（Translation Lookaside Buffer）

**问题**：每次访问虚拟地址，都要先查页表找到物理页号，再访问物理内存。页表查找本身要访问内存，相当于**查地图花的时间比走路还长**。

**类比**：你去小区找 201 房间：
```
传统方式：
  1. 问物业："201 在哪？" → 物业翻查册子（内存访问）
  2. 走到 201（又一次内存访问）
  → 查一次地图要花两次"腿"的时间

TLB 方式：
  1. 先看自己口袋的便签（小缓存）
  2. 便签上有 "201 = 2号楼3层" → 直接去
  3. 命中！只花 1 次时间
```

```
CPU 想访问虚拟地址 0x4040
    │
    ├─ TLB 查找（硬件缓存，并行查找，1 个 CPU 周期）
    │   ├─ 命中 → 直接拿到物理地址
    │   └─ 未命中 → 查页表 → 填充 TLB → 返回
    │
    ▼
物理内存访问
```

**TLB 命中率通常 > 95%**，所以实际效果接近 O(1)。

## 扩展：NUMA-aware 内存管理

### NUMA 架构

**类比**：一个大型小区有多个分区，每个分区有自己的快递柜。

```
        分区 0              分区 1              分区 2              分区 3
      [楼栋A]              [楼栋B]              [楼栋C]              [楼栋D]
      64GB 柜子            64GB 柜子            64GB 柜子            64GB 柜子
         │                    │                    │                    │
         └────────────────────┴────────────────────┴────────────────────┘
                             小区间连接桥（QPI/InfinityBand）

住在楼栋A的人（CPU 0）去本楼栋取快递 → 快（本地）
住在楼栋A的人去楼栋B取快递        → 慢 2-3 倍（跨区，有过桥费）
```

**NUMA（Non-Uniform Memory Access）**：访问"本地"内存快，访问"远程"内存慢。

```bash
# 查看 NUMA 拓扑
numactl --hardware

# 把进程绑定到特定节点（让它用本区的内存）
numactl --membind=0 --cpunodebind=0 python script.py

# 自动选择本地节点
numactl --localalloc python script.py
```

### 透明大页（Transparent Huge Pages）

**问题**：默认页大小 4KB，如果程序用了 10GB 内存，就有 250 万个页。页表太大，查起来慢。

**解法**：把多个小柜子合并成一个大柜子（2MB = 512 个 4KB 柜子合并）。

```bash
# 查看大页配置
cat /sys/kernel/mm/transparent_hugepage/enabled

# 优点：减少页表层级，降低 TLB miss
#   4KB 页：虚拟地址空间 48 位 → 4 级页表
#   2MB 页：只需 3 级页表
# 缺点：内存碎片化、khugepaged 后台扫描开销
```

## 扩展：内存压缩与 OOM Killer

### 内存回收层级（从轻到重）

**类比**：小区快递柜快满了，物业的处理顺序：

```
层级 1：kswapd 守护进程（物业巡逻员，异步回收）
  → 快递柜使用超过 70% 时开始巡逻（watermark_high）
  → 悄悄把很久没开的柜子里的东西搬到地下室暂存区
  → 不影响任何人

层级 2：直接内存回收（有人来拿快递时发现柜子满了）
  → 物业员工帮你当场清出一个柜子
  → 可能会稍微慢一点（你得等）

层级 3：OOM Killer（经理来了，决定开除一户）
  → 实在没地方了
  → 物业选择一户，把那户的所有快递都扔出去
  → dmesg 里可以看到 "Out of memory: Killed process ..."
```

### OOM Score 与 oom_score_adj

```bash
# 查看进程被杀的"意愿分数"（越高越容易被杀）
cat /proc/12345/oom_score

# 调整 OOM 偏好（-1000 到 +1000）
echo -1000 > /proc/12345/oom_score_adj  # 永远不杀（VIP）
echo +1000 > /proc/12345/oom_score_adj  # 优先杀（可牺牲的）
```

**类比**：
```
oom_score_adj = -1000  → 这是物业管理员，不能杀
oom_score_adj = +1000  → 这是乱扔垃圾的租户，优先驱逐
```

### OOM Killer 选择算法

```python
# Linux 6.1+ 使用"能量感知"算法
# 不只是看内存用量，还看"杀掉这个进程能回收多少，能改善多少系统状态"
def select_victim():
    score = oom_score_adj + resident_pages / 1000
    score += pgmajfault_delta           # 最近发生了多少次缺页中断
    score += vm_committed_anon         # 申请了多少内存

    if is_root_process(pid):           # root 进程有保护
        score *= 0.9

    return process_with_highest_score  # 分数最高的杀掉
```

### 防御 OOM 的策略

```bash
# 容器层面：设置内存硬限制，触达后容器内进程收到 SIGKILL
# 这样行为更可预测，不会在宿主机层面乱杀进程
docker run --memory=512m --memory-swap=512m myapp
```

---

## 一句话总结

> **虚拟内存的本质，是让每个进程都以为自己独占了整个内存，通过映射表（页表）把"假的"变成"真的"。**
>
> - **页表**：映射虚拟柜号到物理柜号
> - **TLB**：口袋便签，缓存常用映射，查一次顶两次
> - **LRU/CLOCK**：当柜子满了，选最久没用的那个换出去
> - **OOM Killer**：最后手段，杀一个进程救整个系统
