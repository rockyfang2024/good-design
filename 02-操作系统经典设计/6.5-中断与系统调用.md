# 6.5 中断与系统调用：用户态和内核态的边界

> 用户程序想让内核帮忙做事（读写文件、发送网络包），但内核能访问所有硬件和内存。用户程序可能有 bug，错误的访问会摧毁系统。

---

## 问题

- 内核能访问所有硬件和内存
- 用户程序可能有 bug，错误的访问会摧毁系统
- 需要安全地从用户代码跳转到内核代码，然后安全返回

---

## 经典解法：陷阱门（Trap Gate）

```c
// 用户程序调用 read()
char buf[1024];
read(fd, buf, 1024);

// 编译器把它编译成：
mov  $0, %rax    // syscall 号 (read = 0)
mov  %rdi, %rax  // 参数1: fd
mov  %rsi, %rax  // 参数2: buf
mov  %rdx, %rax  // 参数3: count
syscall          // ← 专门为系统调用设计的指令

// 内核 Trap 处理：
// 1. 保存寄存器（用户态寄存器值）
// 2. 切换到内核栈
// 3. 根据中断号查 IDT（中断描述符表）找到处理函数
// 4. 执行 sys_read()
// 5. 恢复寄存器，返回用户态
// 6. 用户程序继续执行，%rax 里有返回值
```

### 为什么用软中断 `int 0x80` 而不是函数调用？

- 函数调用（`call`）只能跳转到可执行代码段内的地址
- `int 0x80` 是**特权级切换**指令，跳转到内核代码段
- CPU 会自动检查当前 CPL（特权级）≤ 目标段 DPL
- 用户态 CPL=3，内核态 CPL=0，所以能切换

### 现代 Linux：用 `syscall` 指令（更快，2010 年引入）

```c
// 同样调用 read()
mov  $0, %rax
mov  %rdi, %rax
mov  %rsi, %rax
mov  %rdx, %rax
syscall
```

## 扩展：io_uring — 现代异步 I/O

**问题**：传统的 read/write 系统调用是同步的——进程在 I/O 期间必须等待。对于高 IOPS 的数据库，这是巨大的瓶颈。

### 传统方案的问题

- `O_NONBLOCK` + `epoll`（Reactor 模式）：I/O 非阻塞但仍需要两次上下文切换（用户→内核→用户）
- `aio`：Linux 旧版异步 I/O，不支持文件，只支持块设备

### io_uring（Linux 5.1+，2019）

```c
// 创建 io_uring 实例
struct io_uring ring;
io_uring_setup(32, &params);

// 提交读请求（完全异步，不阻塞）
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, sizeof(buf), 0);
io_uring_submit(&ring);  // 立即返回，不等待完成

// 等待完成（可以批量）
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
io_uring_cqe_seen(&ring, cqe);
```

### io_uring 的性能优势

```
传统系统调用：
  用户态 → 内核 → 返回（但数据还在传递）
                 ↓
          完成后通知（POLLIN/ring buffer）
                 ↓
          用户态读取结果

性能差距：
  - 传统：每 I/O 需要 3-5 次系统调用（准备、提交、等待、收集）
  - io_uring：提交和完成可以在同一个系统调用里
  - 甚至完全零系统调用（polling 模式）
  - SQLite 在 io_uring 模式下 QPS 提升 2-3 倍
```

### 应用场景

```
数据库（SQLite/PostgreSQL）→ 高频磁盘 I/O
高性能 Web 服务器 → 减少 syscall 开销
视频流媒体 → 高吞吐顺序读写
日志收集系统 → 异步批量写入
```
