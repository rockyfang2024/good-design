# 6.5 中断与系统调用：用户态和内核态的边界

> 用户程序想让内核帮忙做事（读写文件、发送网络包），但内核能访问所有硬件和内存。用户程序可能有 bug，错误的访问会摧毁系统。
>
> **类比**：写字楼里，普通员工不能直接进档案室（财务档案、客户合同），必须有前台帮忙传递。前台会检查你要求的内容是否合规，防止你拿走不该拿的东西，或者塞进去不合规的文件。

---

## 生活场景：银行柜台

```
你去银行：
1. 你坐在柜台外面（用户态），不能直接进金库（内核态）
2. 你填一张申请单（系统调用参数）
3. 柜员（内核）帮你办理：
   - 查你的账户余额
   - 从金库拿钱
   - 把钱交给你
4. 你拿钱走人（回到用户态）

关键点：
- 你不知道金库在哪、怎么开锁
- 柜员帮你做所有"危险操作"
- 如果你填的申请有问题，柜员会拒绝（返回错误）
- 你不能闯进金库抢东西
```

---

## 问题

- 内核能访问所有硬件和内存
- 用户程序可能有 bug，错误的访问会摧毁系统
- 需要安全地从用户代码跳转到内核代码，然后安全返回

---

## 经典解法：陷阱门（Trap Gate）

### 系统调用的工作原理

**类比**：柜员不是你自己进去，而是"你把申请单递进去，柜员帮你做"。

```c
// 用户程序想读文件
char buf[1024];
read(fd, buf, 1024);

// 编译后变成（伪汇编）：
mov  $0, %rax    // syscall 号，read = 0（在 Linux 中）
mov  %rdi, %rsi   // 参数1: fd
mov  %rsi, %rdx   // 参数2: buf（用户空间地址）
mov  %rdx, %r10   // 参数3: count
syscall           // ← 按下"叫柜员"按钮

// 内核做的事：
// 1. 保存寄存器（你的申请表内容）
// 2. 切换到内核栈（柜员的工作台）
// 3. 根据 syscall 号找到对应的处理函数（查服务手册）
// 4. 执行 sys_read()
// 5. 恢复寄存器，把结果放到 %rax（你拿到的回执）
// 6. 返回用户态
```

### 特权级与保护

**类比**：为什么不能直接闯进金库？因为你有"用户卡"，柜员有"管理员卡"。

```
x86 的 4 个特权级（RING 0-3）：

RING 0（内核态）：什么都能干，可以访问任意内存地址
RING 3（用户态）：只能访问用户空间，不能直接碰硬件

你去银行：
- 你（RING 3）：只能填表、递材料、拿结果
- 柜员（RING 0）：可以进金库、操作一切

CPU 检查：
- CPL（当前特权级）≤ 目标段的 DPL，才能跳过去
- 用户态 CPL=3，内核态 CPL=0，所以能切换
- 反过来？内核想跳到用户态？可以直接跳转（因为内核可以降级）
```

### 软中断 `int 0x80` vs `syscall` 指令

```
int 0x80（旧方式）：
  - 用"中断门"进入内核
  - CPU 查 IDT（中断描述符表）找到处理函数
  - 触发方式：软件主动触发

syscall（现代方式，2010 年引入）：
  - 专门为系统调用设计，速度更快
  - 不查表，直接跳转到固定地址（MSR 寄存器配置）
  - 少了"中断开销"，性能更好
```

## 扩展：io_uring —— 不用等的"预约制"银行

### 传统系统调用的瓶颈

**类比**：传统的 read/write 是"同步排队"——你递上申请单，然后站在柜台前等柜员处理完。

```
同步 I/O（你站在柜台前等）：
  你：我要取 100 万
  柜员：稍等，我要去金库数钱
  你：站在那等...（阻塞）
  柜员：好，钱给你
  你：走人

问题：
  - 你等的时候什么都干不了（进程阻塞）
  - 柜员也走不开（线程阻塞）
  - 如果同时有 10000 个人来取钱，就要 10000 个柜员
```

### io_uring（Linux 5.1+，2019）——"预约+快递"模式

**类比**：你去银行，不是排队等，而是：
1. 把申请单投进"预约箱"（提交队列）
2. 柜员从箱子里取单子，按自己的节奏处理
3. 处理完成后，结果放到"取件箱"（完成队列）
4. 你有空的时候来取件箱拿结果

```
传统方式：
  用户 → 柜员 → 用户  （全程同步，你在等）

io_uring 方式：
  用户把任务投进预约箱（立即返回，不等）
  柜员按自己的节奏从预约箱取任务
  用户从取件箱取结果（可以批量取）
```

```c
// 创建 io_uring 实例
struct io_uring ring;
io_uring_setup(32, &params);

// 提交读请求（完全异步，立即返回）
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, sizeof(buf), 0);
io_uring_submit(&ring);  // ← 立即返回，不等待完成！

// 等待完成（可以批量等待多个 I/O）
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
io_uring_cqe_seen(&ring, cqe);
```

### io_uring 的性能优势

```
传统系统调用：
  用户态 → 内核 → 返回（但数据还在传递）
                 ↓
          完成后通知
                 ↓
          用户态读取结果

性能差距：
  - 传统：每 I/O 需要多次系统调用（准备、提交、等待、收集）
  - io_uring：提交和完成可以在同一个系统调用里
  - 甚至完全零系统调用（polling 模式，轮询取件箱）
  - SQLite 在 io_uring 模式下 QPS 提升 2-3 倍
```

### 应用场景

```
数据库（SQLite/PostgreSQL）→ 高频磁盘 I/O，io_uring 大幅降低延迟
高性能 Web 服务器（Nginx）→ 减少 syscall 开销
视频流媒体 → 高吞吐顺序读写
日志收集系统 → 异步批量写入，吞吐量翻倍
```

## 中断的两种类型

```
硬件中断（外部）：
  - 网卡收到数据包 → 通知 CPU
  - 键盘按键 → 通知 CPU
  - 就像前台说："有人找你"

异常/软件中断（内部）：
  - 除零错误 → CPU 自动触发
  - 系统调用（int 0x80 / syscall）→ 主动触发
  - 就像你自己打电话给老板
```

---

## 一句话总结

> **系统调用的本质，是给用户程序一个"受控入口"进入内核——像银行柜台一样，用户递申请，内核做危险的事，结果安全返回。**
>
> - **Trap Gate**：用户态到内核态的安全门
> - **syscall**：更快、更专用的触发指令
> - **io_uring**：从"同步排队"到"预约+快递"，让 I/O 不阻塞
