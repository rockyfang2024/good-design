# 6.7 进程与线程：调度粒度与资源隔离

> 进程切换代价高（3-5 微秒），线程切换代价低（0.5-1 微秒）。什么时候用进程？什么时候用线程？

---

## 问题

- 进程切换代价高：需要切换页表、寄存器、打开文件、内存映射
- 线程切换代价低：只切换寄存器和栈，同一进程内共享内存
- 隔离 vs 共享：安全和性能永远在权衡

---

## 线程的三种使用场景

```
1. 并行计算（CPU 密集）
   → 多线程利用多核，每个线程做独立计算
   → 共享内存通信（极快）

2. I/O 异步化（I/O 密集）
   → 主线程发起 I/O 后不阻塞，继续做其他事
   → I/O 完成后线程被唤醒
   → 典型：异步网络服务器（nginx, redis）

3. 简化并发模型
   → 每个客户端一个线程处理
   → 比单线程事件循环更易编程（但扩展性差）
```

## 进程的使用场景

```
1. 隔离不同任务（一个崩溃不影响其他）
   → Web 服务器：每个请求一个进程（早期 Apache）

2. 需要不同特权/资源
   → 浏览器：渲染进程、网络进程、GPU 进程隔离

3. 多语言协作
   → Python 进程调用 C 进程，通过 RPC 通信
```

**现代趋势**：Go 的 Goroutine（轻量级协程）、Rust 的 async/await，用更小的调度粒度解决传统线程的瓶颈。

## 扩展：cgroup 与容器资源隔离

**问题**：如何让多个进程组之间互不干扰？限制 CPU、内存、IO、PID 数量等。

### Linux cgroup（Control Groups）

```
cgroup 层级：
  root
  ├── system.slice（系统服务）
  │   ├── nginx.service
  │   └── sshd.service
  ├── user.slice（用户会话）
  │   └── user@1000.service
  └── docker（容器）
      ├── abc123
      └── def456
```

### cgroup v2 资源控制

```bash
# 创建子 cgroup
mkdir -p /sys/fs/cgroup/memory/myapp

# 内存限制
echo "512M" > /sys/fs/cgroup/memory/myapp/memory.max
echo "512M" > /sys/fs/cgroup/memory/myapp/memory.swap.max

# CPU 限制
echo "100000 100000" > /sys/fs/cgroup/memory/myapp/cpu.max
# 100000/100000 = 100% of one CPU

# PID 数量限制（防止 fork 炸弹）
echo "100" > /sys/fs/cgroup/pids/myapp/pids.max

# IO 限制（blkio）
echo "8:0 wbps=10485760" > /sys/fs/cgroup/io/myapp/io.max
# 限制为 10MB/s

# 把进程加入 cgroup
echo $PID > /sys/fs/cgroup/memory/myapp/cgroup.procs
```

### namespace 隔离（容器的另一面）

```bash
# 六个 namespace 隔离维度
# PID namespace：容器内看到独立的进程树
# Network namespace：容器有独立的网络栈
# Mount namespace：容器有独立的文件系统视图
# UTS namespace：容器有独立的主机名
# IPC namespace：容器有独立的 System V IPC
# User namespace：容器内用户映射到宿主机不同用户

# 查看进程所属 namespace
ls -la /proc/$$/ns/
```

### cgroup + namespace = 容器

```
cgroup  → 资源限制（能用什么）
namespace → 视图隔离（能看到什么）

组合起来 = 容器（像虚拟机一样隔离，但共享内核）
```
