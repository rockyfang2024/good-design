# 6.7 进程与线程：调度粒度与资源隔离

> 进程切换代价高（3-5 微秒），线程切换代价低（0.5-1 微秒）。什么时候用进程？什么时候用线程？
>
> **类比**：进程就像"独栋别墅"——每户有自己的水表、电表、门牌号，改装水管不影响邻居。线程就像"合租公寓"——室友共享厨房和卫生间，一个室友把厨房水管弄爆了，大家都要被淹。

---

## 生活场景：独栋别墅 vs 合租公寓

```
独栋别墅（进程）：
  每户有自己的：
    - 水表、电表（独立的资源）
    - 门牌号（独立的地址空间）
    - 花园（独立的内存）
  优点：一户出问题不影响其他户
  缺点：每户进门要刷卡（切换慢）

合租公寓（线程）：
  室友们共享：
    - 厨房、卫生间（共享的地址空间）
    - 电费按房间分摊（共享 CPU）
  优点：进出方便（切换快），共享东西不用出门
  缺点：一个室友把厨房弄乱了，大家都被淹
```

---

## 问题

- 进程切换代价高：需要切换页表、寄存器、打开文件、内存映射
- 线程切换代价低：只切换寄存器和栈，同一进程内共享内存
- 隔离 vs 共享：安全和性能永远在权衡

---

## 什么时候用进程？

```
1. 需要隔离不同任务（一个崩溃不影响其他）
   → Web 服务器早期（Apache）：每个请求一个进程
   → 一个请求崩溃了，其他请求继续服务

2. 需要不同特权/资源
   → 浏览器：渲染进程、网络进程、GPU 进程隔离
   → 恶意网页的 JS 崩溃了，不能让它把整个浏览器搞死

3. 多语言协作
   → Python 进程调用 C 进程，通过 RPC 通信
   → 各自用最适合的语言，不互相限制

4. 需要长期运行、不互相干扰
   → 数据库主进程 + 备份进程
   → systemd 管理的系统服务
```

---

## 什么时候用线程？

```
1. 并行计算（CPU 密集）
   → 多线程利用多核
   → 图像处理：把图片分成 4 块，4 个线程同时处理
   → 共享内存通信（极快）

2. I/O 异步化（I/O 密集）
   → 主线程发起 I/O 后不阻塞，继续做其他事
   → I/O 完成后线程被唤醒
   → 典型：异步网络服务器（nginx、redis）

3. 需要快速响应
   → GUI 应用：主线程响应用户点击，后台线程加载数据
   → 游戏引擎：渲染线程 + 物理计算线程 + AI 线程
```

---

## 线程的三种使用场景

```
1. 并行计算（CPU 密集）
   线程A ──┐
   线程B ──┼──→ 共享内存（通信极快）
   线程C ──┤
   线程D ──┘
   典型：图像渲染、科学计算

2. I/O 异步化（I/O 密集）
   主线程: 发起 read() ──→ 不阻塞，继续执行其他任务
   线程B: 等待 I/O 完成 ──→ 回调处理
   典型：异步网络服务器、高并发服务器

3. 简化并发模型
   每个客户端一个线程 ──→ 比单线程事件循环更易编程
   缺点：线程数太多时上下文切换开销大
```

---

## 进程 vs 线程对比

```
维度            进程                    线程
─────────────────────────────────────────────────────
切换成本        3-5 微秒               0.5-1 微秒
内存            独立的地址空间          共享地址空间
通信            需 IPC（管道/消息）    直接读写共享变量
隔离性          强（一进程崩溃不传染）  弱（一个线程崩溃影响全进程）
创建速度        慢（要分配独立资源）    快（共享进程资源）
调度            操作系统完全控制       操作系统控制（但更轻量）
```

## 扩展：Goroutine 与轻量级协程

**传统线程的问题**：每个线程占用 1-8MB 栈内存，1000 个线程就是 1-8GB。

**类比**：如果每个参加婚礼的客人都要占一个包厢（传统线程），1000 个客人就要 1000 个包厢。但如果用"婚礼大厅+圆桌"（协程），1000 个客人坐 100 张桌子，共享空间。

```
Go 的 Goroutine：
  - 初始栈 2KB（可动态增长）
  - 由 Go 运行时调度，不是操作系统调度
  - 百万级并发而不吃力
  - 内部基于多路复用（一个 OS 线程上跑多个 goroutine）
```

**Rust 的 async/await**：
```rust
async fn fetch_data() {
    let resp = http_get("https://api.example.com").await;
    // await 期间，这个 goroutine 让出线程
    // 其他任务可以复用这个线程
}
```

## 扩展：cgroup 与容器资源隔离

**问题**：如何让多个进程组之间互不干扰？限制 CPU、内存、IO、PID 数量等。

### cgroup 层级

**类比**：小区物业管理系统，规定了每户（cgroup）的资源配额。

```
cgroup 层级：
root（小区物业）
├── system.slice（公共服务区）
│   ├── nginx.service（前台服务）
│   └── sshd.service（安保服务）
├── user.slice（住户区）
│   └── user@1000.service（1000 号住户的服务）
└── docker（民宿区）
    ├── abc123（民宿 A）
    └── def456（民宿 B）
```

### cgroup v2 资源控制

```bash
# 创建子 cgroup
mkdir -p /sys/fs/cgroup/memory/myapp

# 内存限制（不能超过 512MB）
echo "512M" > /sys/fs/cgroup/memory/myapp/memory.max
echo "512M" > /sys/fs/cgroup/memory/myapp/memory.swap.max

# CPU 限制（只能用 50% 的一个 CPU）
echo "50000 100000" > /sys/fs/cgroup/memory/myapp/cpu.max

# PID 数量限制（防止 fork 炸弹——无限生孩子）
echo "100" > /sys/fs/cgroup/pids/myapp/pids.max

# 把进程加入 cgroup
echo $PID > /sys/fs/cgroup/memory/myapp/cgroup.procs
```

### namespace 隔离（容器的另一面）

**类比**：每户人家有自己的"视野"——张三只能看到他家阳台，看不到李四家的厨房。

```bash
# 六个 namespace 隔离维度
PID namespace   → 容器内看到独立的进程树（看不到宿主机进程）
Network namespace → 容器有独立的网络栈（自己的 IP 地址）
Mount namespace → 容器有独立的文件系统视图
UTS namespace   → 容器有独立的主机名（hostname）
IPC namespace   → 容器有独立的 System V IPC（信号量、消息队列）
User namespace   → 容器内用户映射到宿主机不同用户（容器的 root=宿主机的普通用户）

# 查看进程所属 namespace
ls -la /proc/$$/ns/
```

### cgroup + namespace = 容器

```
cgroup  → 资源限制（能用什么，最多用多少）
namespace → 视图隔离（能看到什么，感知不到其他容器）

组合起来 = 容器
  像虚拟机一样隔离，但共享内核（更轻量）
  类似公寓 vs 独栋别墅——容器是"有隔断的共享公寓"，虚拟机是"完全独栋"
```

---

## 一句话总结

> **进程是"隔离的盒子"，线程是"盒子里的并行通道"。选择哪种，取决于你需要"安全隔离"还是"高效共享"。**
>
> - **进程**：适合需要隔离、独立运行、不怕切换慢的场景
> - **线程**：适合需要共享数据、快速响应的场景
> - **轻量级协程**（Goroutine/async）：用更小的调度粒度解决传统线程的瓶颈
> - **cgroup + namespace**：让进程组既有资源限制，又有视图隔离——这就是容器
