> 操作系统是计算机科学中最古老的工程领域之一。很多今天 AI Agent 用到的设计思想，在几十年前的操作系统里就已经被解决过了。本章整理操作系统中最经典的设计问题，以及对应的优雅解决方案。

## 6.1 调度问题：谁该获得 CPU？

### 问题

系统里有 N 个进程/线程竞争 CPU 时间，CPU 只有 1 个。怎么分配？

- 交互进程需要快速响应（几毫秒）
- 后台批处理需要高吞吐（完成更多任务）
- 有些进程是 CPU 密集型，有些是 I/O 密集型
- 不能让任何进程"饿死"

### 经典解法

#### 方案 A：多级反馈队列（MLFQ）

```
队列 0（最高优先级）: RR, 时间片=8ms   ← 交互进程
队列 1（中优先级）  : RR, 时间片=16ms
队列 2（低优先级）  : RR, 时间片=32ms  ← 批处理
队列 3（更低优先级）: FCFS             ← 沉睡进程
```

**规则：**
1. 新进程先入队列 0
2. 用完时间片还没完成 → 降级到下一队列
3. I/O 阻塞后 → 提升回高优先级（I/O 密集型会被照顾）
4. 每层队列用完才去下一层

**效果**：
- 短任务（交互）快速完成
- 长任务自动沉底，不饿死短任务
- I/O 密集型自动获得高优先级

这是 **BSD Unix** 和早期 Windows 使用的方案。

#### 方案 B：CFS（完全公平调度器，Linux）

不给每个进程分配固定时间片，而是维护一棵**红黑树**：

```
                时间线 →
进程A ████░░░░░░░░░  已运行 30ms
进程B ██░░░░░░░░░░░░  已运行 10ms
进程C ████████████░░  已运行 80ms ← 需要被调度

按"已运行时间"排序，最少的最高优先 → CFS 总选择最"饿"的
```

**核心思想**：不是"时间片轮转"，而是"让每个进程都公平地获得 CPU"。

CFS 的关键参数：
- `sched_latency`：一个调度周期多长（默认 6ms）
- `minGranularity`：最小时间粒度（防止切换太频繁）
- `nice` 值：权重，越大优先级越低

#### 对比

| 维度 | MLFQ | CFS |
|------|------|-----|
| 核心思想 | 多层队列降级 | 完美公平的红黑树 |
| 响应速度 | 快（高优先级先跑） | 取决于树的深度（通常也很快） |
| 吞吐 | 中等（可能有调度开销） | 高（树操作 O(log n)） |
| 复杂度 | 中等 | 高 |
| 代表系统 | BSD, Windows NT | Linux |

### 扩展：实时调度（RT Scheduling）

**问题**：工业控制、医疗设备、机器人——这些场景要求调度延迟可预测，且有上限。

**实时系统分类**：

```
硬实时（Hard Real-Time）：错过截止时间 = 灾难性故障
  → 航空控制系统、医疗输液泵
  → 调度策略：Rate Monotonic (RM) / Earliest Deadline First (EDF)

软实时（Soft Real-Time）：偶尔错过截止时间可接受
  → 视频播放（丢帧可以，但卡顿不行）
  → 调度策略：POSIX 实时调度（SCHED_FIFO / SCHED_RR / SCHED_DEADLINE）
```

**Linux 实时调度配置**：

```bash
# 查看当前调度策略
chrt -p $$

# 将进程设为 FIFO 实时调度，优先级 50
chrt -f 50 -p 12345

# DEADLINE 调度（最硬核的实时）：任务有三元组 (runtime, period, deadline)
chrt -d --sched-runtime 100000 --sched-deadline 200000 --sched-period 300000 -p 12345
```

**实时性的代价**：优先级高的任务会抢占其他任务，可能导致"饿死"。普通进程的延迟无法保证。

### 扩展：组调度与 CPU Bandwidth Controller

**问题**：一个捣乱进程可能吃掉整台机器的 CPU。怎么限制"每个用户/组/容器"最多只能用 X% 的 CPU？

**解决方案**：Linux CFS Group Scheduler + CPU Bandwidth Controller

```bash
# 创建一个 CPU bandwidth controller（cgroup v2）
# 限制整个 group 最多使用 50% 的 CPU 时间

# /sys/fs/cgroup/system.slice/background.service/cpu.max
# 格式：max 或 "quota period"
echo "50000 100000" > /sys/fs/cgroup/system.slice/background.service/cpu.max
# 50000/100000 = 50% CPU 带宽
```

**CFS 带宽控制器算法**：

```python
# 每个周期（period），每个组最多只能使用 quota 的时间
def check_bandwidth(cgroup):
    used = cgroup.cpu_usage_this_period
    quota = cgroup.cpu_quota

    if used > quota:
        # 这个 cgroup 超过配额，暂停调度直到下个周期
        throttle(cgroup)
    else:
        schedule(cgroup)
```

## 6.2 内存管理：虚拟内存

### 问题

- 物理内存只有 4GB，但运行了 100 个进程
- 每个进程都可能崩溃，不能让一个进程的 bug 影响到其他进程
- 程序大小可能超过物理内存（部分加载）
- 需要让进程觉得自己有"连续完整"的地址空间

### 经典解法：虚拟内存 + 分页

**虚拟地址空间（每个进程独立的）**：

```
0x00000000  ┌─────────────────┐
            │     代码段       │ 0x400000
            ├─────────────────┤
            │     数据段       │
            ├─────────────────┤
            │     堆（向上生长）│ ← malloc 分配这里
            │                 │
            │    （空闲）      │
            │                 │
            │    栈（向下生长）│ ← 函数调用
0xBFFFFFFF  └─────────────────┘
```

**物理内存被切成固定大小的"页"（通常 4KB）**，通过页表映射：

```
虚拟页 0  →  物理页 7
虚拟页 1  →  物理页 3
虚拟页 2  →  [不在内存，在磁盘 swap 区]
虚拟页 3  →  物理页 1
```

**页表条目（PTE）结构**：

```c
struct PageTableEntry {
    uint8_t  present: 1;    // 页面是否在内存
    uint8_t  writable: 1;   // 是否可写
    uint8_t  user: 1;       // 用户态可访问？
    uint16_t physical_page;  // 物理页号
    uint8_t  accessed: 1;   // 被访问过（用于置换）
    uint8_t  dirty: 1;      // 被修改过（换出时需要写回）
    // ...
};
```

### 页置换算法

当物理内存满了，需要把某个页换到磁盘。经典的 4 种算法：

#### LRU（最近最少使用）

```python
# 每次访问页，把它移到"最近使用"队列的末尾
# 需要淘汰时，淘汰队列头（最久未使用的）
memory_pages = ["A", "B", "C"]  # 最左=最久未用

def access(page):
    memory_pages.remove(page)
    memory_pages.append(page)  # 移到末尾

def evict():
    return memory_pages.pop(0)  # 淘汰最老的
```

**问题**：LRU 需要维护有序队列，复杂度 O(n)；且在某些访问模式（顺序扫描）下性能极差（每访问一次都移动一次）。

#### CLOCK（第二次机会）

```python
# 用一个环形缓冲区和"使用位"
# 指针循环遍历：
#   - 如果使用位=1 → 清零，移到下一页（给第二次机会）
#   - 如果使用位=0 → 淘汰
pages = ["A", "B", "C", "D"]  # 使用位=[1, 0, 1, 0]
pointer = 0

def find_evict():
    while True:
        if pages[pointer].used:
            pages[pointer].used = 0  # 第二次机会
            pointer = (pointer + 1) % len(pages)
        else:
            return pointer  # 这个页要被淘汰
```

**为什么用 CLOCK 而不是 LRU**：
- LRU 需要每次访问都更新队列（代价高）
- CLOCK 只需要置位/清位，指针顺时针移动，O(1)

#### 工作集模型

```python
# 观察：大部分进程只使用"活跃"的少量页面
# "工作集" = 最近 W 次访问的页面集合
# 如果一个页面不在工作集里，很快就会被淘汰

def should_evict(page, working_set):
    return page not in working_set  # 不在工作集的优先淘汰
```

**核心洞察**：程序有局部性——当前用到的数据/代码，很快会再用到；很久没用的数据，可能很久都不会用。LRU/CLOCK 就是利用这个特性。

### TLB（Translation Lookaside Buffer）

页表查找是 O(1) 但有 2-3 次内存访问，代价高。加一个缓存：

```
CPU 想要访问虚拟地址 0x4040
    │
    ├─ TLB 查找（硬件缓存，并行）
    │   ├─ 命中 → 直接拿到物理地址（1 个周期）
    │   └─ 未命中 → 查页表 → 填充 TLB → 返回
    │
    ▼
物理内存访问
```

TLB 命中率通常 > 95%，所以实际效果接近 O(1)。

### 扩展：NUMA -aware 内存管理

**问题**：多路服务器中，CPU 和内存被分成多个"节点"，访问本地内存比访问远程内存快 2-3 倍。怎么让进程尽量用本地内存？

**NUMA 架构**：

```
        CPU 0           CPU 1           CPU 2           CPU 3
      [核心]          [核心]          [核心]          [核心]
         │               │               │               │
      [内存节点0]     [内存节点1]     [内存节点2]     [内存节点3]
       64GB            64GB            64GB            64GB
         │               │               │               │
         └───────────────┴───────────────┴───────────────┘
                        QPI/InfinityBand 互联
```

**Linux NUMA 策略**：

```bash
# 查看 NUMA 拓扑
numactl --hardware

# 查看当前进程的 NUMA 亲和
numactl --show

# 把进程绑定到特定节点
numactl --membind=0 --cpunodebind=0 python script.py

# 自动选择本地节点
numactl --localalloc python script.py
```

**透明大页（Transparent Huge Pages）**：

```bash
# 查看大页配置
cat /sys/kernel/mm/transparent_hugepage/enabled

# 优点：减少页表层级，降低 TLB miss
#   4KB 页：虚拟地址空间 48 位 → 4 级页表
#   2MB 页：只需 3 级页表，TLB 条目更少
#
# 缺点：内存碎片化、khugepaged 扫描开销
# 生产环境建议：madvise 模式下启用（只对明确申请的大页生效）
```

### 扩展：内存压缩与 OOM Killer

**问题**：内存耗尽时，系统不能直接崩溃。需要优雅地回收内存或杀掉不重要的进程。

**内存回收层级**（从轻到重）：

```
层级 1：kswapd 守护进程（异步回收）
  → 当可用内存低于 watermark_high，开始kswapd
  → 扫描不活跃的 LRU 链表，尝试换出页面
  → 不阻塞任何进程

层级 2：直接内存回收（direct reclaim）
  → 当进程分配内存但没有足够可用页
  → 进程自己触发回收（可能阻塞）
  → 导致性能抖动（application stalls）

层级 3：OOM Killer
  → 所有回收手段失败
  → Linux 选择"最该死"的进程杀掉
  → dmesg 里可以看到 "Out of memory: Killed process ..."
```

**OOM Score 与 oom_score_adj**：

```bash
# 查看进程 OOM score（越高越容易被杀）
cat /proc/12345/oom_score

# 调整 OOM 偏好（-1000 到 +1000）
# 设为 -1000：永远不杀
# 设为 +1000：优先杀
echo -1000 > /proc/12345/oom_score_adj
```

**OOM Killer 选择算法**：

```python
# Linux 6.1+ 使用 "能量感知" 算法
def select_victim():
    score = oom_score_adj + resident_pages / 1000  # 内存占用因子
    score += pgmajfault_delta                        # 最近发生 major fault 的增量
    score += vm_committed_anon                       # 匿名页（可回收）

    # 加上进程特权惩罚（root 进程稍难杀）
    if is_root_process(pid):
        score *= 0.9

    return process_with_highest_score
```

**防御 OOM 的策略**：

```bash
# 容器层面：设置 memory limit，让容器在达到限制时触发 cgroup OOM
# 而不是让系统 OOM Killer 介入

# docker 示例
docker run --memory=512m --memory-swap=512m myapp
# 达到 limit 时，容器内的进程收到 SIGKILL（更可预测的行为）
```

## 6.3 同步互斥：让并发安全

### 问题

两个进程同时操作共享资源（计数器、链表、文件）：

```
进程 A: read count → 5
进程 B: read count → 5
进程 A: write count → 6   (基于旧的 5)
进程 B: write count → 6   (基于旧的 5)  ← 错误！应该是 7
```

这是经典的 **Race Condition（竞态条件）**。

### 经典解法

#### 互斥锁（Mutex）

```python
lock = Mutex()

def critical_section():
    lock.acquire()     # 拿锁，阻塞等待
    count += 1         # 临界区：同时只有一个进程能进来
    lock.release()     # 放锁

# 使用
critical_section()     # 进程 A
critical_section()     # 进程 B（必须等 A 释放）
```

**Mutex 的实现（硬件支持）**：

```c
// TAS (Test-and-Set) 指令 - 原子操作
bool test_and_set(bool *target) {
    bool old = *target;   // 读
    *target = true;      // 写
    return old;          // 返回旧值
}

// 自旋锁实现
void lock(bool *mutex) {
    while (test_and_set(mutex) == true) {
        // 忙等待（自旋）- 浪费 CPU，但等待时间短时很快
    }
}

void unlock(bool *mutex) {
    *mutex = false;
}
```

**为什么不能直接用普通读/写**：

```c
// 这不是原子操作（两条指令）
// 其他 CPU 核心可能在这两步之间看到中间状态
old = *mutex;
*mutex = true;
```

#### 信号量（Semaphore）

Mutex 只能被一个进程持有。**信号量**可以控制 N 个资源：

```python
from threading import Semaphore

# 10 个连接池，信号量控制并发上限
pool = Semaphore(10)

def handle_request():
    pool.acquire()     # 获取一个连接（阻塞直到有空闲）
    try:
        # 处理请求
    finally:
        pool.release()  # 归还连接
```

**Semaphore 的实现**：

```c
struct Semaphore {
    int value;
    Queue waiters;      // 等待队列
};

void P(Semaphore *s) {  // wait / acquire
    atomic_decrement(&s->value);
    if (s->value < 0) {
        // 资源耗尽，睡眠并加入等待队列
        block_current_process(s->waiters);
    }
}

void V(Semaphore *s) {  // signal / release
    atomic_increment(&s->value);
    if (s->value <= 0) {
        // 有等待者，唤醒一个
        wake_one_process(s->waiters);
    }
}
```

**注意**：`P()` 和 `V()` 本身必须是**原子操作**——在多核上需要硬件指令（CAS、LL/SC）配合。

#### 读写锁

```python
# 读可以并发（多个读者不冲突）
# 写必须独占（写者与所有读者互斥）
rwlock = ReadWriteLock()

def read_data():
    with rwlock.read_lock():
        return data  # 多个读可以同时进行

def write_data():
    with rwlock.write_lock():
        data = new_data  # 写的时候没有人能读或写
```

#### 死锁的四个必要条件（破坏任一即可）

```python
# 1. 互斥：资源只能被一个进程占用
#    → 无法破坏（有些资源本质上是互斥的）

# 2. 持有并等待：进程持有资源同时请求更多
#    → 破坏：要么一次性申请所有资源，要么不持有时再申请

# 3. 不可抢占：已分配资源不能被强制夺走
#    → 破坏：允许内核强制剥夺资源

# 4. 循环等待：形成 P1→P2→...→Pn→P1 的等待链
#    → 破坏：给所有资源编号，必须按顺序申请（资源有序化）
```

### RCU（Read-Copy-Update）

对于读多写少场景：

```python
# 读：完全无锁，极快
def read():
    return data  # 直接访问，无需加锁

# 写：不是原地修改，而是复制+替换
def write(new_value):
    old = data
    new_data = new_value  # 复制
    # 在某个同步点（grace period）后释放旧数据
    defer_free(old)
```

**核心思想**：读操作永远不被阻塞（无锁读）；写操作创建副本，替换指针，所有读者读到新版本后再释放旧版本。

Linux 内核大量使用 RCU 来保护链表、树等数据结构。

### 扩展：内核中的锁与无锁数据结构

**问题**：内核里同时有中断处理、软中断、进程上下文——同一段代码可能从不同上下文被调用。怎么保证同步安全？

**Linux 内核的五种上下文**：

```
进程上下文（process context）→ 可以睡眠，可以获取信号量
  ↑                                        ↓
中断处理（interrupt handler）→ 不可睡眠，只能用自旋锁
软中断（softirq）→ 不可睡眠，用于高频率事件（网络、块设备）
tasklet→ 基于软中断，不能睡眠
工作队列（workqueue）→ 可以睡眠，在进程上下文执行
```

**自旋锁 vs 信号量选择**：

```c
// 规则：
// 1. 中断上下文 → 只能用自旋锁
// 2. 进程上下文且可能睡眠 → 信号量
// 3. 进程上下文且不能睡眠 → 自旋锁

// 中断上下文获取锁（自动禁用该 IRQ）
spin_lock_irqsave(&my_lock, flags);
// ... 临界区 ...
spin_unlock_irqrestore(&my_lock, flags);

// 进程上下文获取锁
spin_lock(&my_lock);
// ... 临界区 ...
spin_unlock(&my_lock);

// 可以睡眠的进程上下文
down(&my_semaphore);  // 获取信号量（可能睡眠）
// ... 临界区 ...
up(&my_semaphore);    // 释放信号量
```

**Linux 内核的无锁数据结构**：

```c
// 1. percpu 计数器（无锁，每个 CPU 独立计数）
DEFINE_PER_CPU(long, my_counter);

// 2. RCU（读多写少场景）
rcu_read_lock();
struct my_struct *p = rcu_dereference(global_ptr);
// 使用 p ...
rcu_read_unlock();
// writer: 写端用 rcu_assign_pointer() + synchronize_rcu()

// 3. x86 原子指令
atomic_inc(&counter);           // 原子 +1
atomic_add_return(5, &counter); // 原子 +=5 并返回结果
cmpxchg(&old_val, new_val, ptr); // CAS（Compare-And-Swap）
```

## 6.4 文件系统：如何持久化存储

### 问题

磁盘上要存几十亿个文件，每个文件有名字、大小、时间戳、内容。怎么组织？

- 文件名变长、变短 → 不能预分配固定大小
- 删除文件 → 产生空洞，不能浪费空间
- 目录层级深 → 需要高效查找
- 突然断电 → 不能丢数据

### 经典解法

#### inode + 块组（Unix 文件系统的基石）

```
磁盘布局：
┌─────────┬────────────┬─────────────┬────────────┐
│ Super   │ Block      │  inode 表   │  数据块    │
│ Block   │ Group      │  (索引节点) │            │
│(文件系统│ Descriptors│             │            │
│ 元数据) │            │  inode 0   │  block 0   │
└─────────┴────────────┴────────────┴────────────┘

inode 结构（ext2/ext3/ext4）：
┌──────────┬──────────────────────────────┐
│ metadata │  data blocks (直接/间接/双间接)│
├──────────┼──────────────────────────────┤
│ mode     │  block[12]   ← 12个直接块     │
│ uid      │  block[12]   ← 1K * 12 = 12KB │
│ size     │  block[13]   ← 单间接块指针   │
│ atime    │  block[14]   ← 双间接块指针   │
│ mtime    │  block[15]   ← 三间接块指针   │
│ blocks   │  ...                        │
│ links    │                              │
└──────────┴──────────────────────────────┘
            每个块 1KB → 最大文件 4GB+（用间接块扩展）
```

**为什么用 inode 而非连续分配**：

```
连续分配：文件 A 占 block 0-9，文件 B 占 block 10-19
→ 问题：删了 A，空出 block 0-9，B 不能自动长大填进去 → 碎片化

inode：文件是 block 指针的集合
→ 文件可以散布在磁盘任何位置，按需分配
→ 删除文件只是释放指针指向的块，不影响其他文件
```

#### 日志文件系统（Journaling）

**问题**：写文件时突然断电，可能只写了一半，文件系统进入不一致状态。

**解法**：Write-Ahead Log（日志）

```
正常文件系统写入：
    直接写磁盘（可能有中间不一致状态）

日志文件系统写入：
    1. 把要写的东西先记到"日志区"（顺序写入，很快）
       - TxB: 开始事务
       - [要修改的块内容]
       - TxE: 结束事务

    2. 确认日志落盘后，再去修改实际位置（后台）

    3. 完成后标记日志为"完成"
       （或者不用标记，TxB/TxE 本身就是标记）

崩溃恢复：
    检查日志 → 有未完成事务 → 重做（REDO）或撤销（UNDO）
    → 文件系统恢复到一致状态
```

**代表系统**：ext3/ext4, NTFS, JFS, XFS 都使用日志（只是 ext3/ext4 是"日志数据"模式，而 ext4 是"日志摘要"模式更复杂）。

#### 命名管道（FIFO）与 UNIX Domain Socket

同一台机器上进程间通信：

```
进程 A（生产者）                          进程 B（消费者）
      │                                       ▲
      │ write("hello")                        │
      ├─────────────────── pipe ──────────────┤
      │                                       │
```

```c
// 创建管道
int pipefd[2];
pipe(pipefd);  // pipefd[0]=读端, pipefd[1]=写端

// 写
write(pipefd[1], "hello", 5);

// 读
read(pipefd[0], buf, 5);
```

**管道是字节流**（没有消息边界），**Socket 是消息边界**。

### 扩展：VFS（虚拟文件系统层）

**问题**：Linux 需要同时支持 ext4、XFS、Btrfs、NFS、CIFS……几十种文件系统。每种接口都不一样。怎么让应用程序用统一的接口访问所有文件系统？

**解决方案：VFS 抽象层**

```
                应用程序
                   │
        open() read() write() mkdir()  ← 统一的 POSIX API
                   │
          ┌────────┴────────┐
          ▼                 ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │   ext4   │    │   XFS    │    │   NFS    │
    │ 文件系统  │    │ 文件系统  │    │ 文件系统  │
    └──────────┘    └──────────┘    └──────────┘
          ▲                 ▲            ▲
          └────────┬────────┴────────────┘
                   ▼
            VFS（虚拟文件系统层）
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
  super_block  inode   dentry
    (整个文件系统)  (单个文件)  (目录项缓存)
```

**VFS 的四个核心对象**：

```c
struct super_block    // 整个文件系统的元数据
struct inode         // 单个文件的元数据（inode）
struct dentry        // 目录项缓存（路径名 → inode 的映射）
struct file          // 进程打开的文件实例（包含读写位置等）

// 每个文件系统必须实现一组操作函数指针
struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int     (*open)(struct inode *, struct file *);
    int     (*release)(struct inode *, struct file *);
    loff_t  (*llseek)(struct file *, loff_t, int);
    // ...
};
```

**dentry 缓存（目录项缓存）**：

```
路径解析：
  /home/ubuntu/file.txt
  ↑
  首先查 dentry 缓存（最近访问的路径）
  ↓ 未命中
  逐级查 inode：root inode → home inode → ubuntu inode → file inode
  ↓
  dentry 缓存会缓存每一级，下次访问时直接命中
```

## 6.5 中断与系统调用：用户态和内核态的边界

### 问题

用户程序想让内核帮忙做事（如读写文件、发送网络包），但：

- 内核能访问所有硬件和内存
- 用户程序可能有 bug，错误的访问会摧毁系统
- 需要安全地从用户代码跳转到内核代码，然后安全返回

### 经典解法：陷阱门（Trap Gate）

```c
// 用户程序调用 read()
char buf[1024];
read(fd, buf, 1024);

// 编译器把它编译成：
mov  $3, %eax    // 系统调用号 3 = read
mov  %rdi, %rax  // 参数1: fd
mov  %rsi, %rax  // 参数2: buf
mov  %rdx, %rax  // 参数3: count
syscall          // ← 专门为系统调用设计的指令

// 内核 Trap 处理：
// 1. 保存寄存器（用户态寄存器值）
// 2. 切换到内核栈
// 3. 根据中断号查 IDT（中断描述符表）找到处理函数
// 4. 执行 sys_read()
// 5. 恢复寄存器，返回用户态
// 6. 用户程序继续执行，%rax 里有返回值
```

**为什么用软中断 `int 0x80` 而不是函数调用**：

- 函数调用（`call`）只能跳转到可执行代码段内的地址
- `int 0x80` 是**特权级切换**指令，跳转到内核代码段
- CPU 会自动检查当前 CPL（特权级）≤ 目标段 DPL
- 用户态 CPL=3，内核态 CPL=0，所以能切换

**现代 Linux 用 `syscall` 指令**（更快，2010 年引入）：

```c
// 同样调用 read()
mov  $0, %rax    // syscall 号
mov  %rdi, %rax  // 参数1: fd
mov  %rsi, %rax  // 参数2: buf
mov  %rdx, %rax  // 参数3: count
syscall          // ← 专门为系统调用设计的指令，比 int 0x80 快
```

### 扩展：io_uring — 现代异步 I/O

**问题**：传统的 read/write 系统调用是同步的——进程在 I/O 期间必须等待。对于高 IOPS 的数据库，这是巨大的瓶颈。

**传统方案**：
- `O_NONBLOCK` + `epoll`（Reactor 模式）：I/O 非阻塞但仍需要两次上下文切换（用户→内核→用户）
- `aio`：Linux 旧版异步 I/O，不支持文件，只支持块设备

**新方案：io_uring（Linux 5.1+，2019）**

```c
// 创建 io_uring 实例
struct io_uring ring;
io_uring_setup(32, &params);  // 32 个 slot

// 提交读请求（完全异步，不阻塞）
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, sizeof(buf), 0);
io_uring_submit(&ring);  // 立即返回，不等待完成

// 等待完成（可以批量）
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
// 处理结果
io_uring_cqe_seen(&ring, cqe);
```

**io_uring 优势**：

```
传统系统调用：
  用户态 → (io_uring) → 内核 → 返回（但数据还在传递）
                 ↓
          完成后通知（POLLIN/ring buffer）
                 ↓
          用户态读取结果

性能差距：
  - 传统：每 I/O 需要 3-5 次系统调用（准备、提交、等待、收集）
  - io_uring：提交和完成可以在同一个系统调用里，甚至完全零系统调用（polling 模式）
  - SQLite 在 io_uring 模式下 QPS 提升 2-3 倍
```

## 6.6 进程间通信：消息传递

### 问题

两个独立进程怎么交换数据？

### 经典解法

#### 共享内存（最快，但需要同步）

```c
// 进程 A：创建共享内存
int shmid = shmget(IPC_KEY, 4096, IPC_CREAT | 0666);
void *shm = shmat(shmid, NULL, 0);
strcpy(shm, "hello from A");

// 进程 B：连接到同一块共享内存
int shmid = shmget(IPC_KEY, 4096, 0666);
void *shm = shmat(shmid, NULL, 0);
printf("%s\n", shm);  // 直接访问，不需要系统调用
```

**注意**：共享内存本身不提供同步，需要额外用 Mutex/Semaphore 保护。

#### 消息队列（System V / POSIX）

```c
// 发送
msgget(key, IPC_CREAT);
msgsnd(qid, &msg, strlen(msg.text), 0);

// 接收
msgrcv(qid, &msg, sizeof(msg.text), msg_type, 0);
```

**消息队列 vs 管道**：

| | 管道 | 消息队列 |
|---|---|---|
| 生命周期 | 随进程（无名）/ 随内核（有命） | 随内核，直到被显式删除 |
| 方向 | 单向（FIFO） | 双向 |
| 消息边界 | 无（字节流） | 有（每条消息独立） |
| 查找 | 只能从头部读 | 可以按 type 随机读 |

---

### 扩展：Linux 内核 IPC 演进

**从 System V 到 POSIX**：

```bash
# System V IPC（传统，但仍广泛使用）
ipcs  # 查看当前 IPC 资源

# 消息队列
msgget() msgsnd() msgrcv()
# 信号量
semget() semop() semctl()
# 共享内存
shmget() shmat() shmdt()

# POSIX IPC（更简单，POSIX 语义）
# 消息队列
mq_open() mq_send() mq_receive()
# 信号量
sem_open() sem_wait() sem_post()
# 共享内存
shm_open() mmap() munmap()
```

**mmap 共享内存 vs shmget**：

```c
// shmget + shmat：System V 共享内存
shmget(IPC_KEY, size, IPC_CREAT);
shmat(shmid, NULL, 0);

// mmap：POSIX 共享内存（文件-backed 或 anonymous）
// 文件-backed（持久化）
int fd = open("/dev/shm/my_shm", O_RDWR);
void *ptr = mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);

// anonymous（不落盘，进程间共享）
void *ptr = mmap(NULL, size, PROT_READ|PROT_WRITE,
                 MAP_ANONYMOUS | MAP_SHARED, -1, 0);
```

## 6.7 调度粒度问题：进程 vs 线程

### 问题

- 进程切换代价高（3-5 微秒）：需要切换页表、寄存器、打开文件、内存映射
- 线程切换代价低（0.5-1 微秒）：只切换寄存器和栈，同一进程内共享内存

什么时候用进程？什么时候用线程？

### 经典解法

**线程的三种使用场景**：

```
1. 并行计算（CPU 密集）
   → 多线程利用多核，每个线程做独立计算
   → 共享内存通信（极快）

2. I/O 异步化（I/O 密集）
   → 主线程发起 I/O 后不阻塞，继续做其他事
   → I/O 完成后线程被唤醒
   → 典型：异步网络服务器（nginx, redis）

3. 简化并发模型
   → 每个客户端一个线程处理
   → 比单线程事件循环更易编程（但扩展性差）
```

**进程的使用场景**：

```
1. 隔离不同任务（一个崩溃不影响其他）
   → Web 服务器：每个请求一个进程（早期 Apache）

2. 需要不同特权/资源
   → 浏览器：渲染进程、网络进程、GPU 进程隔离

3. 多语言协作
   → Python 进程调用 C 进程，通过 RPC 通信
```

**现代趋势**：Go 的 Goroutine（轻量级协程）、Rust 的 async/await，用更小的调度粒度解决传统线程的瓶颈。

cgroup 层级：

## 6.8 零拷贝：从磁盘到网络的捷径

### 问题

传统的数据传递路径：

```
磁盘 ──read()──→ 用户缓冲区 ──write()──→ Socket 缓冲区 ──→ 网络
        ↑                              ↑
      2次拷贝                      2次上下文切换
```

4 次数据拷贝，2 次上下文切换。服务器传输大文件时开销极大。

### 经典解法：sendfile()

```
磁盘 ────→ 用户缓冲区（完全绕过）───→ Socket ──→ 网络
          DMA 零拷贝                 2次系统调用，无用户态copy

Linux 实现：
sendfile(socket_fd, file_fd, NULL, file_size);
      │
      ├─ DMA 把文件内容复制到 Socket 缓冲区（内核内部）
      ├─ 协议栈封装 TCP/IP 头
      └─ 网卡发送
```

**零拷贝的关键**：CPU 不参与数据搬运，数据直接在 内核缓冲区 之间传递。

**更先进的方案：RDMA（远程直接内存访问）**：

```
传统：CPU 参与数据拷贝
RDMA：网卡直接读写另一台机器的内存，CPU 零参与
      网络 ──DMA──→ 对方内存（零拷贝、零 CPU 开销）

用于：高性能计算集群、分布式数据库（InfiniBand）
```

---

### 扩展：DPDK 与高性能网络

**问题**：传统 Linux 网络栈经过多次上下文切换（网卡→内核→用户），在 100Gbps 级别遇到瓶颈。怎么绕过内核？

**解决方案：DPDK（Data Plane Development Kit）**

```
传统路径（每包）：
  网卡 → 内核驱动 → Linux 内核网络栈 → 用户态
  （每步都有中断、上下文切换、内存拷贝）

DPDK 路径（轮询模式）：
  网卡 → DPDK 驱动 → 用户态（完全绕过内核）
  （无中断、无上下文切换，polling 模式）

DPDK 工作原理：
  1. 锁定网卡（igb_uio/vfio 驱动）
  2. 用户进程直接读写网卡的 DMA 环形缓冲区
  3. 用大页（HugePages）避免 TLB miss
  4. 零拷贝：网包数据直接送到用户态的 mbuf
```

**DPDK vs io_uring vs 传统 select/epoll**：

```
场景：10Gbps 网络，64 字节小包

传统方案：最多 ~1Mpps（每秒百万包）
io_uring：~2-3Mpps（减少系统调用开销）
DPDK：~10-15Mpps（完全绕过内核）

代价：
  - DPDK 需要专用 CPU 核（不能运行其他任务）
  - 需要大页内存（2MB/1GB）
  - 无法与其他进程共享网卡
  - 开发复杂度高

典型应用：高性能负载均衡器（DPDK + VPP）、金融交易系统、5G UPF
```

## 6.10 内核调度器的演进：从 O(1) 到 EEVDF

### 问题

Linux 2.6 之前，调度器是 O(n) 的——进程越多，调度越慢。2.6 引入了 O(1) 调度器，但存在"交互感知差"问题。后来又被 CFS 取代。Linux 6.6 又引入了 EEVDF（Earliest Eligible Virtual Deadline First）。

### 各代调度器对比

```
O(n) 调度器（Linux 2.4）：
  → 每次调度遍历所有进程，找到最高优先级
  → 进程数增加时，调度延迟线性增长

O(1) 调度器（Linux 2.6.0）：
  → 每个优先级一个运行队列，调度 O(1)
  → 问题：交互进程优先权是静态的，批处理会"偷"走交互时间

CFS（Linux 2.6.23，2007）：
  → 红黑树，按虚拟运行时间排序
  → 完全公平，但响应延迟不理想（"湿地效应"）
  → 问题：I/O 密集型任务可能饿得太久

EEVDF（Linux 6.6，2023）：
  → 取代 CFS，成为默认调度器
  → 思想：每个进程有 "eligible time" 和 "deadline"
  → 优先调度"最早符合条件的进程"
  → 同时照顾延迟（交互）和吞吐（批处理）
```

**EEVDF 算法示意**：

```python
# 每个任务有两个属性
class Task:
    eligible_time   # 最早可以被调度的时间
    deadline        # 最晚必须完成的时间

# 调度决策：选 eligible time 最小的任务
def pick_next():
    # 只考虑 deadline > eligible time 的任务
    candidates = [t for t in runqueue if t.deadline > t.eligible_time]
    return min(candidates, key=lambda t: t.deadline)
```

**为什么 EEVDF 更好**：
- CFS 的问题是"公平但不一定及时"
- EEVDF 保证：任务在 deadline 之前一定被调度
- 同时维护了公平性（eligible time 机制）

## 6.11 本章设计思想总结

操作系统几十年解决的核心问题，与现代 Agent 系统面临的问题高度相通：

```
操作系统问题          →    AI Agent 对应设计
─────────────────────────────────────────────────────
进程调度（谁先用）     →    LLM 调用的 Budget 控制（iteration_budget）
虚拟内存（给每个进程独立空间）→ Session 隔离（不同 session_id 不混淆）
页置换算法（内存不足时换出）→ Context 压缩（历史太长时压缩中间段）
Mutex/Semaphore（并发安全）→ 工具执行的并发控制（_should_parallelize_tool_batch）
RCU（读多写少优化）    →    Session 历史只读，append-only
日志文件系统（断电恢复）→    Trajectory 保存（会话轨迹持久化）
中断/系统调用（安全边界）→   危险工具的 approval 审批链
零拷贝（减少不必要的数据搬运）→ Prompt Caching（减少重复传输）
cgroup（资源隔离）      →    多租户 Agent 的资源配额
OOM Killer（内存压力下的决策）→ LLM 降级策略（模型降级、回复截断）
EEVDF（延迟敏感任务调度）→    流式输出的优先级调度
```

**理解操作系统设计，是理解所有复杂系统设计的基石。**
