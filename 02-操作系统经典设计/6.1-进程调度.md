# 6.1 进程调度：谁该获得 CPU？

> 操作系统最核心的问题之一：当 CPU 只有 1 个，但进程有 N 个时，怎么分配？
>
> **类比**：就像一家只有 10 个座位的餐厅，但有 100 个人在排队等位。经理需要决定：谁先坐、谁能插队、谁愿意等久一点。

---

## 生活场景：餐厅叫号的艺术

想象你去一家热门餐厅吃饭：

```
门口队伍：
1. 张三（刚到，等了 0 分钟）—— VIP，要见重要客户
2. 李四（等了 5 分钟）—— 普通散客
3. 王五（等了 30 分钟）—— 已经快饿晕了
4. 赵六（等了 2 小时）—— 订了包厢的客人
5. 钱七（等了半天，但还没到）—— 电话预约，还没进店
```

**操作系统面临同样的问题**：
- **VIP 客人** = 交互进程（你敲键盘，浏览器要立刻响应）
- **快饿晕的客人** = 已经等了很久的后台任务（不能无限期等下去）
- **订包厢的客人** = 有硬截止时间的实时任务（视频帧必须在 16ms 内渲染）
- **还没到的预约客人** = 还在睡眠的进程（I/O 完成后会被唤醒）

---

## 问题

- 交互进程需要快速响应（几毫秒）
- 后台批处理需要高吞吐（完成更多任务）
- 有些进程是 CPU 密集型，有些是 I/O 密集型
- 不能让任何进程"饿死"（等太久）

---

## 经典解法

### 方案一：时间片轮转（Round Robin）

**类比**：服务员按顺序叫号，每个客人最多坐 10 分钟，时间到了就换下一位。

```
时间片 = 10ms
t=0ms:  进程A 开始运行
t=10ms: 时间片用完 → 切换到进程B
t=20ms: 时间片用完 → 切换到进程C
t=30ms: 时间片用完 → 切换回进程A
```

**问题**：如果每个客人都坐满 10 分钟，100 个人就要等 1 秒钟才能轮到自己。对于只想问个事的客人来说太久了。

---

### 方案二：多级反馈队列（MLFQ）——"能插队"的智能叫号

**核心思想**：让"等了很久的人"有机会插队，但"待不久的人"可以优先。

```
队列 0（最高优先级，8ms）:  刚到、等了一会儿的客人
队列 1（中优先级，16ms）:   等了比较久的客人
队列 2（低优先级，32ms）:   等了很久、可能要坐很久的客人
队列 3（最低）:            沉睡中的客人（睡着了，等人叫醒）
```

**规则**（MLFQ 的 4 条铁律）：

1. **新人先排队 0**（新到的客人先去 VIP 区）
2. **坐满了还没吃完 → 降级**（你拿了 8 分钟还没吃完？去普通区）
3. **等很久还没轮到自己 → 升级**（等太久了？给你插队到 VIP 区）
4. **每层队列用完了才去下一层**

**现实例子**：
```
你去银行办事：
1. 刚进门 → 取号机给你 A01（VIP 号）
2. 等了 5 分钟没人理 → 自动升级到 A02（优先号）
3. 又等了 10 分钟 → 再升级到 A03（贵宾专属通道）
4. 终于轮到你了，但你是来存钱的（简单业务）→ 2 分钟搞定，不用换窗口
5. 你朋友是来办信用卡的（复杂业务）→ 时间到了还没办完，请换到下一个窗口
```

**MLFQ 的真实历史**：Windows NT 和 BSD Unix 都用过这个方案。它**自动识别**哪些是"快餐客人"（I/O 密集型），哪些是"长饭客人"（CPU 密集型）。

---

### 方案三：CFS（完全公平调度器）——"谁饿得最厉害谁先吃"

**类比**：不是按顺序叫号，而是服务员始终选择**等得最久**的那个人。

```
CFS 维护一棵"等待时间树"：
餐厅大堂
├── 王五（等最久：30分钟）
├── 张三（等了一会儿：10分钟）
└── 李四（刚坐下：2分钟）

→ 下一个一定是王五（因为等最久）
```

**与 MLFQ 的核心区别**：

| | MLFQ | CFS |
|---|---|---|
| 核心思想 | 多层队列，动态升降级 | 完美公平，始终选"等最久的" |
| 响应速度 | 快（高优先级先跑） | 取决于树的深度（通常也很快） |
| 吞吐 | 中等 | 高（树操作 O(log n)） |
| 谁适合 | 交互+批处理混合 | 需要公平性的场景 |

**Linux 的 CFS 参数**：

```bash
# 一个调度周期多长（默认 6ms）
cat /proc/sys/kernel/sched_latency_ns

# 最小时间粒度（防止切换太频繁）
cat /proc/sys/kernel/sched_min_granularity_ns
```

## 扩展：实时调度（RT Scheduling）

**场景**：医院的输液泵、飞机的自动驾驶系统——这些场景不能"等一等"，必须在截止时间前完成，否则出人命。

**实时系统分类**：

```
硬实时（Hard Real-Time）：错过截止时间 = 灾难性故障
  → 飞机自动驾驶：必须在 1ms 内响应传感器数据
  → 心脏起搏器：绝对不能在关键时刻延迟
  → 策略：Rate Monotonic（周期短的任务优先级高）/ EDF（最紧急的先做）

软实时（Soft Real-Time）：偶尔错过截止时间可接受
  → 你看视频：偶尔丢一帧没关系，但不能一直卡
  → 视频帧必须在 16ms 内渲染下一帧，但偶尔超时没事
  → 策略：POSIX 实时调度（SCHED_FIFO / SCHED_RR / SCHED_DEADLINE）
```

**Linux 实时调度配置**：

```bash
# 查看当前调度策略
chrt -p $$

# 将进程设为 FIFO 实时调度，优先级 50（1-99）
chrt -f 50 -p 12345

# DEADLINE 调度（最硬核的实时）：任务有三元组
# runtime=我每次最多跑多久, period=我多久需要跑一次, deadline=我最迟多久必须完成
chrt -d --sched-runtime 100000 --sched-deadline 200000 --sched-period 300000 -p 12345
```

**警告**：实时进程优先级极高，会抢走普通进程的执行时间，可能导致普通进程"饿死"。

## 扩展：组调度与 CPU Bandwidth Controller

**问题**：一个捣乱的进程可能把整台机器的 CPU 吃光。怎么限制"每个用户/组/容器"最多只能用 50% 的 CPU？

**类比**：一家餐厅有 10 张桌子，其中 3 张被某个旅行团包了（50 人），另外散客（7 张桌子）被其他客人占用。

```bash
# 限制 background.service 这个 cgroup 最多用 50% CPU
# 格式：quota period（50000/100000 = 50%）
echo "50000 100000" > /sys/fs/cgroup/system.slice/background.service/cpu.max
```

**带宽控制算法**：

```python
def check_bandwidth(cgroup):
    used = cgroup.cpu_usage_this_period
    quota = cgroup.cpu_quota

    if used > quota:
        # 这个 cgroup 超过配额，暂停调度直到下个周期
        # 像餐厅里包桌的客人点完菜后，服务员先服务其他桌
        throttle(cgroup)
    else:
        schedule(cgroup)
```

---

## 一句话总结

> **调度器的本质，是在"谁更需要马上执行"和"让每个人都公平"之间找平衡。**
>
> - **MLFQ**：智能插队系统，让短任务快进快出，让饿了很久的任务插队
> - **CFS**：完美公平，让等最久的人先吃
> - **实时调度**：有截止时间的任务优先，"救命的事先做"
