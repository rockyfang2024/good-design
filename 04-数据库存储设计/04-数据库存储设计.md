## 4.1 B树与B+树：磁盘索引的基石

### 问题

假设你有 1TB 数据，查询需要 10 秒。怎么让查询在毫秒级完成？

核心挑战：**磁盘比内存慢 10,000 倍**。每次随机读都是一次昂贵的磁盘寻址。

### 经典解法：B树

```python
# B树的核心思想：节点有多个子节点（扇出大），树很浅
# 一棵 3 层 B树，每个节点 100 个子节点 → 100万键

class BTreeNode:
    def __init__(self, max_keys=100):
        self.keys = []        # 排序的键
        self.children = []    # 子节点指针
        self.is_leaf = False

    def search(self, key):
        # 二分查找当前节点
        i = binary_search(self.keys, key)
        if i < len(self.keys) and self.keys[i] == key:
            return self.children[i + 1]  # 找到
        elif self.is_leaf:
            return None  # 没找到
        else:
            return self.children[i].search(key)  # 继续找子节点
```

**为什么 B树适合磁盘**：

```
磁盘页 4KB → B树节点通常 4KB
每个节点 100 个键 → 树高 3 → 最多 3 次磁盘读 → 查询 3ms
```

**磁盘亲和设计**：
- 节点大小 = 磁盘页大小（或倍数）→ 每次读一个节点只需要一次磁盘 IO
- 键按顺序存储 → 范围查询只需要顺着一个叶子链读，不需要回溯

### B+树的进化

```
B树：所有键值都存在节点里，叶子之间没有链接
B+树：只有叶子节点存数据，内部节点只存索引；叶子之间用链表相连
```

**B+树的磁盘友好特性**：

```python
# 内部节点（只存索引）
# [key1, key2, key3] + [ptr1, ptr2, ptr3, ptr4]
#              ↓             ↓
#         小于 key1      key1-key2 之间    ...

# 叶子节点（存实际数据，用链表串联）
# [data1] → [data2] → [data3] → ...
# 支持顺序遍历，不需要从根重新查找
```

**MySQL InnoDB 的主键索引**就是 B+树：
- 叶子节点存完整的行数据（聚簇索引）
- 主键索引叶子节点之间有双向链表，支持范围扫描

## 4.2 LSM树：写优化的存储引擎

### 问题

写入频繁（每秒钟 10 万次），查询也要快。磁盘顺序写比随机写快 10-100 倍，但随机读还是需要。怎么办？

### 经典解法：LSM树（Log-Structured Merge Tree）

**核心思想**：把随机写变成顺序写 + 定期合并（SSTable compaction）。

```
写入流程：
内存（MemTable） → 顺序写 WAL（预写日志） → 内存满了
     ↓
刷盘成 SSTable（Level 0）
     ↓
定期合并（Compaction）：把多个 SSTable 合并成一个，按键排序
```

**SSTable 结构**：

```
SSTable = 有序键值对集合，分块（block）存储

[block 0: keys a-d] [block 1: keys e-g] [block 2: keys h-k]
     ↓                    ↓                    ↓
Bloom Filter          Bloom Filter          Bloom Filter
（快速判断某个键是否在这个 block 中）
```

**为什么 LSM 比 B树更适合写入**：

```
B树写入：
  找到页 → 读入内存 → 修改 → 写回磁盘（随机写，至少 2 次 IO）

LSM 写入：
  追加到 MemTable → 满了就刷成新的 SSTable（顺序写）
  更新不存在，只存在合并时去重（延迟删除）
```

**LSM 的 trade-off**：

| 维度 | B树 | LSM |
|------|-----|-----|
| 写吞吐 | 中（随机写） | 高（顺序写） |
| 读延迟 | O(log n) 单次 IO | 可能需要检查多个 SSTable |
| 空间放大 | 低（原地更新） | 高（合并前有冗余） |
| 写放大 | 低 | 高（合并会重写数据） |

**代表系统**：LevelDB、RocksDB、Cassandra、WiredTiger（MongoDB）

## 4.3 WAL（预写日志）：数据库崩溃恢复的保障

### 问题

事务进行到一半，系统崩溃。怎么保证不丢数据？

### 经典解法：Write-Ahead Log

**核心原则**：在数据写入磁盘之前，先把操作记到日志里。

```
事务提交流程：
1. 日志先行：把"要做的事"先记到 WAL（顺序写，很快）
2. 内存更新：修改内存中的数据
3. 异步刷盘：数据最终写到数据文件

崩溃恢复：
- 重放 WAL：从头读日志，把已经记到日志但还没刷盘的操作重做
- 系统恢复到一致状态
```

**WAL 格式**：

```python
# WAL 记录
record = {
    'txn_id': 12345,
    'lsn': 99999,        # log sequence number
    'op': 'UPDATE',
    'table': 'users',
    'row_id': 789,
    'before': {...},     # 修改前的值（用于 UNDO）
    'after': {...},      # 修改后的值（用于 REDO）
}
```

**ARIES 算法**（IBM 的经典算法）：

```python
# WAL 的三个阶段
def crash_recovery():
    # 1. 分析阶段（Analysis）：找出崩溃前最后的状态
    # 2. 重做阶段（REDO）：从检查点重做所有已记录的操作
    # 3. 回滚阶段（UNDO）：回滚未完成的事务
```

**实际应用**：
- PostgreSQL 的 WAL
- MySQL InnoDB 的 redo log
- 所有主流数据库的崩溃恢复机制

## 4.4 事务隔离级别：并发控制的核心

### 问题

两个事务同时运行，会发生什么？

```python
T1: 读取余额 = 1000
T2: 读取余额 = 1000
T1: 余额 + 100 → 写入 1100
T2: 余额 + 100 → 写入 1100  ← 应该 1200，但只有 1100
```

这是经典的**脏读（dirty read）**。

### 四种隔离级别

```python
# SQL 标准定义的隔离级别（从低到高）

1. READ UNCOMMITTED   # 可以读到其他事务未提交的修改
                       # 可能脏读

2. READ COMMITTED     # 只能读到已提交的修改
                       # 仍然可能不可重复读（同一个事务两次读结果不同）

3. REPEATABLE READ    # 同一事务中多次读结果一致
                       # 可能幻读（范围查询出现新行）

4. SERIALIZABLE       # 强制事务串行执行
                       # 完全安全，但性能最差
```

### 脏读、不可重复读、幻读

```
脏读：读到其他事务未提交的修改
     T1: update users set balance=0 where id=1
     T2: select balance from users where id=1  → 0（脏）
     T1: rollback
     T2: 用这个脏数据继续操作 → 错误

不可重复读：同一事务中，两次读同一行结果不同
     T1: select balance from users where id=1  → 1000
     T2: update users set balance=2000 where id=1
     T2: commit
     T1: select balance from users where id=1  → 2000（不可重复）

幻读：同一事务中，两次范围查询结果不同
     T1: select count(*) from users where age > 30  → 5
     T2: insert into users (age) values (35)
     T2: commit
     T1: select count(*) from users where age > 30  → 6（幻读）
```

### MVCC：多版本并发控制

**核心思想**：每个事务看到的是"快照"，不是当前最新状态。

```python
# PostgreSQL 的 MVCC 实现

class Transaction:
    def __init__(self, txid):
        self.txid = txid
        self.snapshot = get_active_txids()  # 拍快照

    def read(self, row):
        # 找最新可见的版本
        for version in row.versions:
            if version.created_by_txid in snapshot.visible:
                if version.deleted_by_txid not in snapshot.visible:
                    return version.data  # 返回快照中的值
```

**MVCC 的优势**：
- 读不阻塞写，写不阻塞读（读写分离）
- 事务可以在快照上工作，不被其他事务干扰

## 4.5 分布式数据库的分片策略

### 问题

单库数据量太大（超过 1TB），单表行数太多（超过 10 亿）。怎么把数据分散到多台机器？

### 经典解法

**方案 A：哈希分片（Hash Sharding）**

```python
# 按主键哈希决定数据落在哪个分片
def get_shard(key, num_shards):
    hash_val = hash(key)
    return hash_val % num_shards

# 优点：数据分布均匀
# 缺点：按范围查询需要跨所有分片（分散-聚集查询）
```

**方案 B：范围分片（Range Sharding）**

```python
# 按主键范围划分
shards = [
    (0, 100000, 'shard0'),
    (100000, 200000, 'shard1'),
    (200000, 300000, 'shard2'),
]

def get_shard(key):
    for start, end, shard in shards:
        if start <= key < end:
            return shard
```

**优点**：范围查询高效（如用户 Feed，按时间范围）
**缺点**：容易出现热点（某些分片数据量特别大）

**方案 C：一致性哈希 + 虚拟节点**

```python
class ConsistentHashRing:
    def __init__(self, num_virtual_nodes=150):
        self.ring = {}  # 哈希值 → 物理节点

    def add_node(self, node):
        for i in range(self.num_virtual_nodes):
            hash_key = hash(f"{node}_{i}")
            self.ring[hash_key] = node

    def get_node(self, key):
        hash_key = hash(key)
        sorted_keys = sorted(self.ring.keys())
        for k in sorted_keys:
            if hash_key <= k:
                return self.ring[k]
        return self.ring[sorted_keys[0]]
```

**优势**：节点增减时，数据迁移量最小（只有邻居受影响）
