## 6.1 没有银弹：所有设计都是权衡

### 核心原则

Fred Brooks 在《人月神话》中写道：**"没有银弹能承诺在 10 年内把软件工程的生产力、可靠性或简洁性提升一个数量级。"**

这句话在 1986 年是对的，今天依然正确。

### 为什么永远有权衡

```
简单 vs 正确：简单意味着可能不完整
性能 vs 可读性：极致优化往往伤害可读性
通用 vs 专用：通用的解法在特定场景下往往不如专用的
复用 vs 定制：复用带来灵活性，但总有不需要的功能
```

**例子：为什么 MySQL 的 utf8mb4 是后来的设计**

```sql
-- 早期的 MySQL utf8 只能存 3 字节的 UTF-8（不支持emoji）
-- 正确支持 4 字节 UTF-8 需要 utf8mb4
-- 原因：历史兼容性、存储考量、当时没有人预测到 emoji 的普及
-- 这不是 bug，是当时条件下的合理选择
```

## 6.2 帕累托原则与 80/20 法则

### 核心洞察

```
80% 的用户只使用 20% 的功能
80% 的性能问题来自 20% 的代码
80% 的 bug 来自 20% 的模块
```

### 应用：性能优化

```python
# 性能分析第一步：找到最慢的 20%
# 不要优化未测量的代码

# 先 profiling，再优化
import cProfile
cProfile.run('your_function()')

# 找到 hotspots 后，评估 ROI
# - 优化 A 可能提升 50% 性能，但只影响 1% 的调用
# - 优化 B 可能只提升 10% 性能，但影响 99% 的调用
```

### 应用：代码质量

```python
# 20% 的代码包含 80% 的 bug
# 先写出错的测试，而不是测试所有代码

# 测试策略：优先覆盖关键路径
# - 支付流程 > 浏览流程
# - 登录/认证 > 普通功能
# - 数据写入 > 数据读取
```

## 6.3 简单性优先：KISS 原则

### Keep It Simple, Stupid

```python
# 复杂的设计往往比简单的设计更脆弱

# 简单方案：单数据库
def get_user(user_id):
    return db.query("SELECT * FROM users WHERE id = ?", user_id)

# 复杂方案：缓存 + 数据库 + 写穿策略
class UserService:
    def __init__(self):
        self.cache = Redis()
        self.db = Database()
        self.write_through = WriteThroughStrategy()

    def get_user(self, user_id):
        user = self.cache.get(user_id)
        if not user:
            user = self.db.read(user_id)
            self.cache.set(user_id, user)
        return user

    def update_user(self, user_id, data):
        # 写穿，写入缓存和数据库
        self.cache.set(user_id, data)
        self.db.write(user_id, data)
        # 处理缓存失效、一致性保证...
```

**什么时候用复杂方案**：只有当简单方案明确无法满足需求时，才引入复杂性。

### YAGNI：You Aren't Gonna Need It

```python
# 不要为"将来可能的需求"提前设计
# 先满足当前需求，再迭代

# 过度设计的例子：
class UserService:
    def __init__(self):
        self.plugin_system = PluginSystem()     # 还没用到
        self.middleware_chain = Middleware()    # 还没用到
        self.extension_api = ExtensionAPI()     # 还没用到
        self.webhook_system = WebhookSystem()   # 还没用到
```

**何时扩展**：只有在需求真正出现时，才把代码设计成可扩展的。过早优化是万恶之源。

## 6.4 优雅降级与容错设计

### 核心思想

系统不会"完美"。硬件会挂，网络会断，用户会误操作。

好的设计是：**假设任意组件都可能失败，并为此做好准备。**

### 断路器模式（Circuit Breaker）

```python
import time

class CircuitBreaker:
    def __init__(self, failure_threshold=5, timeout=60):
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.timeout = timeout
        self.last_failure_time = None
        self.state = 'CLOSED'  # CLOSED → OPEN → HALF_OPEN

    def call(self, func):
        if self.state == 'OPEN':
            if time.time() - self.last_failure_time > self.timeout:
                self.state = 'HALF_OPEN'
            else:
                raise CircuitOpenError()

        try:
            result = func()
            if self.state == 'HALF_OPEN':
                self.state = 'CLOSED'
                self.failure_count = 0
            return result
        except Exception as e:
            self.failure_count += 1
            self.last_failure_time = time.time()
            if self.failure_count >= self.failure_threshold:
                self.state = 'OPEN'
            raise
```

**场景**：远程服务调用。当远程服务持续失败时，断路器"跳闸"，不再尝试调用，直接返回错误，保护下游服务不被拖垮。

### 优雅降级示例

```python
# 新闻网站：图片推荐服务挂了
def get_news_feed():
    try:
        # 优先尝试推荐
        articles = recommendation_service.get_personalized()
        # 过滤、排序...
        return articles
    except RecommendationServiceError:
        # 推荐失败，使用热门文章作为 fallback
        articles = trending_service.get_top()
        return articles
    except Exception:
        # 最后 fallback：编辑精选
        articles = editorial_service.get_picks()
        return articles
```

## 6.5 复杂度守恒定律：复杂性不会消失

### 核心洞察

复杂度是守恒的。

```
你不能消除复杂性，只能转移它
把它从代码转移到配置
把运行时错误转移到编译时错误
把开发者的复杂性转移到用户身上
```

**例子：JSON Schema vs 代码校验**

```python
# 方案 A：运行时校验（复杂性在代码）
def validate_user(data):
    if 'name' not in data:
        raise ValidationError('name required')
    if not isinstance(data['name'], str):
        raise ValidationError('name must be string')
    if len(data['name']) > 100:
        raise ValidationError('name too long')
    # 20 行校验代码

# 方案 B：Schema 声明（复杂性在配置）
user_schema = {
    "type": "object",
    "required": ["name"],
    "properties": {
        "name": {"type": "string", "maxLength": 100}
    }
}
# 一行代码调用
validate(data, user_schema)
```

两种方案复杂度相同，只是**在哪里存放**不同。

## 6.6 技术债务：必须偿还的利息

### 什么是技术债务

Ward Cunningham 发明了这个比喻：技术债务就像金融债务，借款能让你快速启动，但利息会随着时间累积。

**主动债务**：为了赶进度，有意选择"不是最好的方案"。

```python
# 技术债务示例：硬编码配置
DATABASE_URL = 'mysql://localhost:3306/prod'  # 未来需要改成配置的

# 技术债务示例：TODO 注释
def calculate_discount(user):
    # TODO: 这个算法在用户量>100万时会崩溃，需要重构
    return user.base_price * 0.9
```

### 债务管理策略

```python
# 1. 追踪债务：用注释标注、记录到 issue 系统
# 2. 分配时间：每个 sprint 留 20% 时间还债
# 3. 评估利息：长期不还的债务，利息会越来越高（改不动、测不准）
# 4. 优先偿还：高利息债务（影响当前开发的）优先还

# 技术债务利息估算
# - 硬编码：每次换环境需要改代码，利息低
# - 全局状态：新增功能时需要担心副作用，利息高
# - 缺乏测试：每次改动需要大量手动验证，利息高
```

## 6.7 抽象与泄漏：封装的设计原则

### 好的抽象隐藏复杂性

```python
# 好的抽象：文件操作
with open('data.txt', 'w') as f:
    f.write('hello')
# 使用者不需要知道：文件系统怎么管理磁盘块、怎么维护目录结构、怎么处理并发写入

# 坏的抽象：实现泄漏
def save_data(data):
    # 内部实现泄漏到接口
    lock = FilesystemLock()
    lock.acquire()
    fs = get_filesystem()
    inode = fs.allocate_inode(...)
    # ... 20 行后端细节暴露给调用者
```

### 避免抽象泄漏的原则

```
1. 最小化接口：只暴露必要的操作
2. 不要让调用者关心内部状态
3. 错误信息应该描述"是什么问题"，不是"底层怎么实现的"
4. 如果你需要向调用者解释"怎么用才对"，抽象不够好
```
