## 3.1 CAP 定理：一致性、可用性、分区容错性的权衡

### 问题

一个分布式数据库，在网络分区（某几个节点之间断连）时会发生什么？

- 如果继续提供服务（保证可用性），不同分区可能看到不同的数据（失去一致性）
- 如果必须保证数据一致，就必须停服（失去可用性）

你不能同时拥有三者。

### CAP 三角

```
           consistency
              /\
             /  \
            /    \
           /  CP  \
          /   模型  \
    可用性 -------- 分区容错性
          \   AP   /
           \ 模型 /
            \  /
             \/
```

**CP 模型**：优先一致性。牺牲可用性。典型：ZooKeeper、HBase、Redis Cluster（主从切换时）
**AP 模型**：优先可用性。牺牲一致性。典型：Cassandra、DynamoDB、Eureka

### 实际工程选择

| 系统 | 场景 | 选择 |
|------|------|------|
| 银行转账 | 强一致性必须 | CP |
| 社交 feed | 用户先看到就行 | AP |
| DNS | 必须可用 | AP |
| 分布式锁 | 不能重复 | CP |

**本质**：CAP 不是说"三选二"，而是说"在分区发生时，你必须在 C 和 A 之间选一个"。平时没有分区，C 和 A 可以同时保证。

## 3.2 一致性模型：从强到弱

### 问题

分布式系统中，"一致性"有很多层。每种"一致性"都是对程序员的承诺。

### 一致性光谱

```
线性一致性（Linearizability）
        ↓
顺序一致性（Sequential）
        ↓
因果一致性（Causal）
        ↓
写后读（Read-your-writes）
        ↓
会话一致性（Session）
        ↓
最终一致性（Eventual）
```

**线性一致性（最强）**：操作像在单个节点上串行发生，且立即对所有节点可见。代价：每次写入需要同步到多数节点才能返回。

**最终一致性（最弱）**：写入后，允许一段时间的不一致，最终会收敛到相同状态。典型：DynamoDB、Cassandra 的 quorum 读。

**工程权衡**：

```python
# 强一致性：每次读都从主节点读
def read_strong(key):
    leader = get_leader()
    return leader.read(key)

# 最终一致性：读任意副本
def read_eventual(key):
    # 可能读到旧值
    node = any_replica()
    return node.read(key)
```

## 3.3 Raft 一致性算法：更容易理解的共识协议

### 问题

多台机器如何对"谁是主节点"、"数据怎么写入"达成一致？

Raft 通过分解成三个子问题让共识协议更易理解和实现：

```
Raft 分解：
1. Leader 选举
2. 日志复制
3. 安全性保证
```

### Leader 选举

```python
# Raft 节点三种状态
states = ['FOLLOWER', 'CANDIDATE', 'LEADER']

# 选举超时（随机化避免竞争）
election_timeout = random(150, 300)  # ms

# 开始选举
def start_election():
    current_term += 1
    state = CANDIDATE
    votes = 1  # 自己的一票

    for peer in peers:
        if request_vote(peer, term=current_term):
            votes += 1

    if votes > len(peers) / 2:
        become_leader()
```

**关键设计**：
- 随机选举超时避免 split vote（两个候选人都只拿到一半票）
- 一个任期（term）最多只有一个 leader
- 多数投票（majority）保证即使网络分区也只有一个 leader

### 日志复制

```python
# 客户端请求流程
def client_request(command):
    if state == LEADER:
        log.append(command)           # 先追加到本地日志
        for peer in peers:
            replicate_log(peer, log_index)  # 并行复制到 followers
        if majority_ack(log_index):
            apply_to_state_machine(command)  # 日志committed后应用
    else:
        redirect_to_leader()
```

**commit 条件**：日志复制到多数节点，才能 commit。

**安全保证**：
- Leader 不覆盖已被 majority 接受的日志条目
- 只有包含完整已提交日志的节点才能成为 leader

## 3.4 幂等性设计：让重试安全

### 问题

网络超时，客户端重试请求。服务器怎么知道这是"重复"还是"新请求"？

### 经典解法

**方案 A：唯一请求 ID（token）**

```python
# 客户端生成唯一 ID
request_id = uuid4()
headers['X-Request-ID'] = request_id

# 服务器去重缓存
seen = set()  # 实际用 Redis，限制大小

def handle_request(req):
    if req.request_id in seen:
        return cached_response(req.request_id)  # 返回之前的结果
    seen.add(req.request_id)
    result = do_logic(req)
    cache[req.request_id] = result
    return result
```

**方案 B：天然幂等操作**

```python
# DELETE 是幂等的，DELETE 两次结果一样
DELETE /users/123  # 第一次：200 OK，第二次：404 Not Found（但幂等）
# DELETE 第二次返回 404 也是幂等的，因为状态没变

# POST 不是幂等的
POST /users  # 每次都创建新用户
```

**方案 C：状态机 + 版本号**

```python
# 每个资源带版本号
resource = {data: ..., version: 5}

# 更新携带版本号
def update(resource_id, new_data, expected_version):
    current = db.get(resource_id)
    if current.version != expected_version:
        raise ConflictError()
    db.update(resource_id, new_data, version=expected_version+1)
```

**实际组合**：通常用方案 A + 方案 B。天然幂等的用 GET/DELETE，需要去重的用唯一 ID。

## 3.5 负载均衡策略：流量分配的艺术

### 问题

有 10 台服务器，怎么把 100 万 QPS 分配到这 10 台，使得没有一台过载？

### 经典策略

**1. 轮询（Round Robin）**

```python
# 简单，但不考虑服务器性能差异
server_idx = 0
while True:
    server = servers[server_idx % len(servers)]
    server_idx += 1
    yield server
```

**问题**：服务器 A 是 64 核，服务器 B 是 8 核，轮询让 B 过载。

**2. 加权轮询**

```python

    total = sum(weights)
    # ... 选取逻辑
```

**3. 最少连接（Least Connections）**

```python
# 把请求发给当前连接数最少的服务器
def least_connection(request):
    server = min(servers, key=lambda s: s.active_connections)
    server.active_connections += 1
    return server
```

**场景**：长连接服务（如数据库连接池）比轮询好。

**4. 一致性哈希（Consistent Hashing）**

```python
# 把服务器和请求都哈希到环上
# 请求选择顺时针最近的服务器

class ConsistentHash:
    def __init__(self, nodes):
        self.ring = {}
        for node in nodes:
            for i in range(virtual_nodes):
                self.ring[hash(node + str(i))] = node

    def get(self, key):
        hash_val = hash(key)
        for h in sorted(self.ring.keys()):
            if hash_val <= h:
                return self.ring[h]
        return self.ring[min(self.ring.keys())]
```

**优点**：增加/删除节点时，只有少部分请求需要重新分配。
